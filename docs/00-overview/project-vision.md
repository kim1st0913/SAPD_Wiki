# SAPD Wiki 项目愿景

> 状态：`active / current business vision`
>
> 更新日期：2026-07-28

## 产品定位

SAPD Wiki 是面向安全架构设计、知识治理和本地交付的结构化知识系统。它不是静态网站、
文件目录或单次 ETL 项目，而是持续维护以下闭环：

```text
多来源资料 → 结构化知识 → 业务关系 → 可追溯查询
         → 受控更新 → 本地桌面交付 → AI 只读知识访问
```

第一使用者是安全架构知识负责人和项目负责人。系统应让非开发人员能够通过业务材料、
映射规则、审批和人工裁定维护知识，同时由工程门禁保证数据、代码和安装包可复现。

## 要解决的问题

安全架构知识通常散落在不同格式、不同粒度和不同版本的文件中，导致：

- 相同对象名称、定义和关系难以统一；
- 能力、环境、生命周期和标准之间的关系不可见；
- 更新内容容易覆盖已确认数据或失去来源；
- 页面、安装包和 AI 查询可能使用不同版本；
- 用户批注和客户评估容易污染基础知识。

SAPD Wiki 将文件内容转化为带稳定标识、来源证据和关系的知识对象，并把基础知识、
内容资产、用户状态和客户评估分成独立数据域。

## 当前业务版图

| 业务域 | 回答的问题 |
|---|---|
| 安全能力 | 有哪些安全能力与关注点，它们如何映射到技术、管理和标准要求 |
| 信息化环境 | 不同环境与对象需要哪些作用域、服务、模块、措施和安全系统 |
| 生命周期 | 开发和数据生命周期各阶段需要哪些安全活动、策略与技术支撑 |
| 知识与标准 | 术语、对象、控制项、来源证据和跨域关系是什么 |
| 成熟度评估 | 当前和目标能力处于什么水平，依据、差距与改进方向是什么 |
| 用户工作区 | 使用者如何记录批注、复核事项、数据篮和本地工作状态 |
| MCP 知识服务 | 兼容 AI 客户端如何在授权边界内查询同一份正式基础知识 |

## 产品原则

1. **来源可追溯**：正式知识必须能够定位到来源及其版本。
2. **更新可审查**：导入必须经过 staging、校验、审批和可恢复发布。
3. **关系优先**：页面不仅展示条目，还要呈现跨业务域关系。
4. **本地优先**：基础知识、用户状态、客户输入和凭据默认留在本机或受控私有交付域。
5. **职责分离**：后端生成业务事实，前端消费契约；MCP 查询知识，不负责导入。
6. **数据隔离**：基础库、内容资产、用户库和成熟度运行数据不得互相覆盖。
7. **同版交付**：Web、macOS、Windows 和 MCP 的验收必须能关联到明确源码和数据版本。
