# 系统轻量架构说明

本文档定义本地化结构化工作知识库系统的轻量架构。当前阶段只明确系统分层、数据流、模块边界和后续多 Agent 分工，不进入代码实现、接口细节或完整数据库设计。

后端逻辑边界和前后端接口契约以 `docs/01-architecture/backend-interface-design.md` 为准。

## 1. 架构定位

本系统不是普通文件管理器，而是：

```text
本地知识资产管理系统
+ 多来源文件 ETL 系统
+ 结构化数据库
+ 本地知识门户
+ 可审查的数据更新机制
```

系统的核心任务是把 Excel、DOCX、PPT、Draw.io、Markdown 等文件中的内容整理为可查询、可关联、可导出、可追溯来源的知识对象。

## 2. 当前架构原则

- 技术选型以 `docs/01-architecture/technology-decisions.md` 为集中记录。
- 先完成数据定义，再开发功能。
- 先支持最小闭环，再扩展更多文件类型。
- 原始文件必须保留，结构化数据必须可追溯来源。
- 自动导入不能静默覆盖人工编辑。
- 数据更新必须经过暂存、校验、审查和变更记录。
- V1 只做必要能力，AI/RAG、知识图谱和复杂分析后置。
- 主控 Agent 负责统一对象、字段、映射和阶段边界。

## 3. 系统分层

```text
用户工作层
  └─ 本地页面 / 桌面应用

应用功能层
  ├─ 知识浏览
  ├─ 搜索筛选
  ├─ 导入审查
  ├─ 标签分类
  ├─ 关系查看
  └─ 导出备份

业务服务层
  ├─ 知识对象服务
  ├─ 来源文件服务
  ├─ 导入任务服务
  ├─ 变更审查服务
  ├─ 搜索服务
  └─ 导出服务

数据处理层
  ├─ 文件识别
  ├─ 内容抽取
  ├─ 字段映射
  ├─ 清洗标准化
  ├─ 数据校验
  ├─ 暂存 staging
  └─ 入库 load

数据存储层
  ├─ SQLite 正式库
  ├─ SQLite FTS 全文索引
  ├─ 本地原始文件仓库
  ├─ 预览文件仓库
  ├─ 导出文件仓库
  └─ 配置与映射规则
```

## 4. 数据流

### 4.1 首次导入数据流

```text
原始文件
→ 文件登记
→ 计算 hash
→ 内容抽取
→ 字段映射
→ 清洗标准化
→ 数据校验
→ staging 暂存区
→ 人工审查
→ 正式知识库
→ 搜索索引
→ 页面展示 / 导出
```

关键要求：

- 原始文件进入 `data/raw` 或等价文件仓库。
- 每条结构化记录必须保留 `source_file_id` 和 `source_location`。
- 导入过程必须生成 `import_job`。
- 正式入库必须写入 `change_log`。

### 4.2 更新数据流

```text
新文件 / 重新上传文件 / 第三方 ETL 数据
→ 文件 hash 和来源识别
→ 与历史版本比较
→ 生成新增 / 修改 / 删除 / 冲突候选
→ staging 暂存区
→ 人工确认
→ 合并到正式库
→ 写入变更记录
```

关键要求：

- 同名文件不等于同一版本，必须用 hash 判断内容变化。
- 人工编辑字段优先级高于自动导入。
- 删除候选默认只标记，不直接删除正式知识。
- 第三方 ETL 默认进入待审核，不直接入正式库。

### 4.3 查询导出数据流

```text
用户查询条件
→ 搜索 / 筛选 / 关系查询
→ 返回知识条目集合
→ 展示详情与来源
→ 选择导出范围
→ CSV / JSON / Excel / Markdown / HTML / ZIP
```

关键要求：

- 查询结果必须能追溯到来源文件。
- 导出不能只导出页面文本，也应支持结构化字段。
- 全量导出应包含数据库、原始文件、配置和 manifest。

## 5. 核心模块边界

### 5.1 数据定义模块

职责：

- 知识资产盘点；
- 知识对象定义；
- 字段字典；
- 字段映射规则；
- 枚举值和标准分类；
- V1 范围判断。

主要输入：

- `docs/03-import-etl/sample-file-inventory.md`
- `docs/02-data-model/data-dictionary-template.md`
- `docs/03-import-etl/import-rules.md`
- 样例文件

主要输出：

- `knowledge_asset_inventory.xlsx`
- `knowledge_objects.xlsx`
- `field_dictionary.xlsx`
- `mapping_rules.xlsx`

当前阶段优先级最高。字段和映射没有稳定前，不应大规模开发功能页面。

### 5.2 文件与来源管理模块

职责：

- 登记原始文件；
- 保存文件路径、类型、hash、版本；
- 标记文件是否可结构化；
- 管理来源文件状态；
- 支持文件重新导入检测。

边界：

- 只负责来源和文件元数据；
- 不负责解释文件内容的业务含义。

### 5.3 ETL 与映射模块

职责：

- 识别文件类型；
- 抽取 Excel sheet/行、DOCX 标题/段落/表格、PPT 页、Draw.io 节点和连线；
- 按映射规则转换为标准知识对象；
- 执行清洗、标准化、编号生成、关系生成；
- 输出暂存记录和错误记录。

边界：

- 不直接覆盖正式库；
- 不决定业务字段是否有价值；
- 不绕过 staging 和审查流程。

### 5.4 暂存与导入审查模块

职责：

- 保存待导入记录；
- 标记新增、修改、重复、冲突；
- 展示导入预览；
- 支持人工确认、跳过、合并；
- 将确认结果写入正式库。

边界：

- 不负责解析文件；
- 不负责前端页面的展示设计；
- 只处理数据进入正式库前的审查。

### 5.5 知识库核心模块

职责：

- 管理 `knowledge_item`；
- 管理标签、分类、关系；
- 维护来源追踪；
- 提供知识详情；
- 支持版本和状态。

边界：

- 不直接读取原始文件；
- 不处理文件解析；
- 不处理导出格式生成。

### 5.6 搜索与关系查询模块

职责：

- 标题搜索；
- 正文搜索；
- 标签筛选；
- 分类筛选；
- 来源筛选；
- 关系查询；
- 后续可扩展全文检索和语义检索。

边界：

- V1 以关键词和结构化筛选为主；
- AI/RAG 不进入 V1 核心架构。

### 5.7 前端展示模块

职责：

- 知识首页；
- 导入任务页；
- 导入审查页；
- 知识列表页；
- 知识详情页；
- 来源文件页；
- 标签分类页；
- 导出页。

边界：

- 前端不定义核心字段；
- 前端只消费字段字典和数据模型；
- 字段模型未稳定前，只做低保真原型或文档设计。

### 5.8 导出与备份模块

职责：

- 当前查询结果导出；
- 单个知识条目导出；
- 按标签、分类、主题导出；
- 全量数据导出；
- 数据库、原始文件、配置打包备份。

边界：

- 导出规则依赖字段字典；
- 不负责 ETL 导入；
- 不负责知识对象定义。

### 5.9 成熟度分析模块

职责：

- 基于现有安全能力知识库生成客户成熟度评估模板；
- 导入员工填写的客户现状评估模板；
- 将客户现状、证据和人工审查记录匹配到安全能力关注点；
- 按成熟度等级、评分规则和落地要素生成评估结果；
- 输出离线 JSON、Markdown、HTML 报告和图表数据。

边界：

- 成熟度分析模块属于 SAPD Wiki 主工程下的独立业务模块，不是完全独立系统；
- 模块只读复用 `capability_category`、`capability_domain`、`capability`、`capability_focus` 等安全能力知识对象；
- 客户输入、匹配候选、评分结果和报告记录使用 `maturity_*` 专用表或本地运行数据，不写入 `knowledge_items`；
- 客户评估输入、证据和报告默认保存在 `data/maturity/`，不提交 GitHub；
- V1 先以 CLI、Excel 模板、JSON/Markdown/HTML 报告闭环为目标，前端页面后置；
- 前端未来只消费 maturity 模块导出的评估结果和图表数据，不在前端执行匹配、评分或关系推断。

## 6. V1 模块范围

### V1 必须包含

- 数据定义文档和配置模板；
- 文件来源登记；
- Excel 导入 MVP；
- Markdown / DOCX 基础导入；
- staging 暂存区；
- 导入审查；
- SQLite 正式库；
- 知识列表和详情；
- 标签、分类、来源追踪；
- 基础搜索；
- CSV / JSON / Excel 导出；
- 全量备份包。

### V1 暂缓

- Draw.io 深度关系抽取；
- PPT 页内复杂结构解析；
- PDF OCR；
- 复杂知识图谱；
- 多人权限；
- 云同步；
- 原文件回写；
- AI/RAG 问答。

## 7. 主控 Agent 职责

主控 Agent 是本项目的调度者和一致性守门人。当前阶段由 Codex 在本对话中承担。

职责：

- 读取并维护 `AGENTS.md`、`task_plan.md`、`findings.md`、`progress.md`；
- 判断当前阶段和下一步任务；
- 控制 V1 范围；
- 统一知识对象、字段名、映射规则；
- 防止过早开发；
- 识别模块依赖；
- 决定哪些任务可以并行；
- 检查各模块产物是否一致；
- 在每次阶段推进后更新计划和进度。

主控 Agent 不应该：

- 在字段未稳定时要求前端先做完整页面；
- 让 ETL、数据库、前端各自定义字段；
- 把 AI/RAG 放到 V1 起点；
- 跳过 staging 和审查机制；
- 把真实敏感数据默认提交到 GitHub。

## 8. 后续多 Agent 分工

多 Agent 并行应在 Phase 1 产物基本稳定后启动，也就是至少有：

- 知识资产盘点；
- 知识对象清单；
- 字段字典；
- 映射规则；
- V1 最小闭环验收标准。

### 8.1 总控调度 Agent

职责：

- 维护项目计划；
- 拆分任务；
- 管理依赖；
- 审查产物一致性；
- 合并各方向结果；
- 更新 `progress.md`。

输入：

- 全部项目文档；
- 各专业 Agent 的阶段产物。

输出：

- 阶段任务；
- 验收清单；
- 风险和决策记录。

### 8.2 数据定义 Agent

职责：

- 分析样例文件；
- 提取候选知识对象；
- 生成字段字典；
- 维护枚举值和分类；
- 标记 V1/V2/暂缓字段。

输入：

- 样例文件；
- `docs/03-import-etl/sample-file-inventory.md`
- `docs/02-data-model/data-dictionary-template.md`

输出：

- `knowledge_objects.xlsx`
- `field_dictionary.xlsx`
- 字段决策记录。

### 8.3 ETL 与映射 Agent

职责：

- 设计映射规则；
- 实现文件解析；
- 输出导入预览；
- 标记错误、重复和冲突；
- 生成 staging 数据。

输入：

- `mapping_rules.xlsx`

输出：

- ETL 规则；
- 导入预览；
- 错误报告；
- staging 记录。

### 8.4 数据库 Agent

职责：

- 根据字段字典设计 SQLite schema；
- 设计迁移脚本；
- 设计 staging 表；
- 设计 import_job、change_log、source_file 等通用表；
- 设计全文检索索引。

输入：

- 字段字典；
- 知识对象定义；
- 导入审查规则。

输出：

- `docs/02-data-model/data-model.md`
- migration SQL；
- 数据库说明。

### 8.5 功能模块 Agent

职责：

- 设计导入审查；
- 设计知识浏览；
- 设计标签分类；
- 设计关系管理；
- 设计导出备份；
- 形成模块验收标准。

输入：

- 架构文档；

输出：

- 功能模块说明；
- 页面与流程清单；

### 8.6 前端 Agent

职责：

- 设计本地知识门户界面；
- 实现列表、详情、导入审查、来源、导出页面；
- 根据字段字典动态展示不同知识类型；
- 保证页面扩展性。

输入：

- 字段字典；
- 数据模型；
- 功能模块说明。

输出：

- 前端页面；
- 交互流程；
- UI 状态说明。

### 8.7 导出备份 Agent

职责：

- 设计导出格式；
- 设计备份包结构；
- 实现查询结果导出；
- 实现全量导出；
- 生成 manifest。

输入：

- 数据模型；
- 文件仓库结构；
- 导出需求。

输出：

- 导出规则；
- 备份包格式；

### 8.8 测试验收 Agent

职责：

- 用样例文件测试导入；
- 验证字段映射；
- 验证来源追踪；
- 验证冲突处理；
- 验证查询和导出；
- 记录缺陷和修正建议。

输入：

- 样例文件；
- V1 验收标准；
- 当前系统实现。

输出：

- 测试结果；
- 问题清单；
- 修正建议。

## 9. Agent 并行启动条件

不建议现在就大规模并行。满足以下条件后，再开始并行：

- 第一批样例文件已准备；
- 至少 3 类知识对象已确认；
- 通用字段已确认；
- 至少一种文件类型的映射规则已确认；
- V1 最小闭环已确认；
- 主控 Agent 已为各方向划定输入、输出和不可越界事项。

推荐并行顺序：

```text
阶段 A：主控 + 数据定义 Agent
阶段 B：数据库 Agent + ETL Agent
阶段 C：前端 Agent + 功能模块 Agent
阶段 D：导出备份 Agent + 测试验收 Agent
```

## 10. 当前下一步

当前项目还处于 Phase 0 到 Phase 1 的交界处。

下一步不应马上开发，而应开始：

1. 准备 5 到 10 个代表性样例文件；
2. 使用 `docs/03-import-etl/sample-file-inventory.md` 做知识资产盘点；
3. 根据样例文件识别第一批知识对象；
4. 使用 `docs/02-data-model/data-dictionary-template.md` 形成字段字典；
5. 使用 `docs/03-import-etl/import-rules.md` 形成第一批映射规则；
6. 由主控 Agent 判断是否进入工程骨架阶段。
