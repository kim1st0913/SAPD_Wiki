# 顾问端压缩包交付模型

本文档定义 SAPD Wiki 面向咨询顾问用户的第一期交付形态。该形态与内部数据维护 / ETL 开发流程分离，避免把开发命令、导入流程或数据库选择暴露给最终用户。

## 1. 产品定位

第一期顾问端产品是“预置数据的本地知识库应用”，不是让顾问自行安装依赖、导入资料或维护数据库的开发工具。

顾问用户拿到的应是一个压缩包。解压后第一次打开应用，点击一键初始化，系统完成本机数据准备，然后即可浏览、搜索、查看关系和使用知识内容。

顾问端第一期不需要登录，也不需要账号体系、权限分层或用户注册。

## 2. 顾问端用户体验

目标流程：

```text
收到压缩包
→ 解压到本机目录
→ 打开 SAPD Wiki 应用
→ 点击“一键初始化”
→ 系统复制预置数据库和资源到应用数据目录
→ 进入知识库工作台
```

初始化完成后，用户再次打开应用时应直接进入工作台，不再重复询问数据库、原始文件目录或 API 地址。

## 3. 压缩包应包含什么

压缩包内建议包含：

| 内容 | 说明 |
|---|---|
| 桌面应用本体 | Tauri 应用或等价本地桌面壳 |
| 前端静态资源 | 工作台页面、组件、样式和脚本 |
| 本地运行服务 | 内置本地 API 或 Tauri command 数据读取层 |
| 预置 SQLite 数据库 | 已完成 ETL / 审批 / 校验后的正式知识库种子库 |
| 页面数据包 | `capability-workbench.json`、`environment-workbench.json`、`lifecycle-workbench.json`、标准 / 指南等离线数据包 |
| 预览资源 | 幻灯片 PNG、必要的内容预览和展示资源 |
| 初始化 manifest | 记录数据版本、资源清单、hash、构建时间和兼容版本 |
| 用户说明 | 面向顾问的打开、初始化、备份和升级说明 |

压缩包不应要求用户安装 Python、Node.js、SQLite CLI 或开发依赖。

## 4. 一键初始化做什么

一键初始化由应用自动执行，用户只需要点击确认。

初始化动作建议包括：

1. 检查应用数据目录是否存在；
2. 创建目录：
   - `<app_data_dir>/SAPD_Wiki/database/`
   - `<app_data_dir>/SAPD_Wiki/resources/`
   - `<app_data_dir>/SAPD_Wiki/exports/`
   - `<app_data_dir>/SAPD_Wiki/backups/`
3. 将压缩包内预置数据库复制为运行库：
   - 来源：`resources/database/sapd_wiki.seed.sqlite3`
   - 目标：`<app_data_dir>/SAPD_Wiki/database/sapd_wiki.sqlite3`
4. 复制或登记页面数据包和预览资源；
5. 写入初始化状态文件，例如：
   - `<app_data_dir>/SAPD_Wiki/app-state.json`
6. 校验数据库、资源 manifest 和关键文件 hash；
7. 初始化成功后进入工作台。

如果用户数据目录已有同版本运行库，初始化按钮应显示“已初始化”或进入“重新初始化 / 修复”流程，不应静默覆盖用户本地数据。

## 5. 数据库策略

开发阶段默认数据库仍是：

```text
data/database/sapd_wiki.sqlite3
```

发布构建阶段应从开发库整理出顾问端种子库：

```text
resources/database/sapd_wiki.seed.sqlite3
```

顾问端实际运行库应位于：

```text
<app_data_dir>/SAPD_Wiki/database/sapd_wiki.sqlite3
```

顾问端运行库由一键初始化自动创建。用户不需要知道数据库文件位置，也不需要手工选择数据库。

## 6. 顾问端不包含什么

第一期顾问端不提供：

- 登录、注册、账号管理；
- 用户自行导入 Excel / PDF / PPT / DOCX；
- ETL 配置、字段映射编辑、parser 调试；
- 数据库路径选择；
- 命令行操作入口；
- 原始敏感样例文件；
- 开发备份库和历史中间产物。

导入、清洗、审批、校验、数据包生成和发布构建属于内部维护流程，由项目维护者或 Codex 在构建前完成。

## 7. 内部维护流程和顾问端流程边界

内部维护流程：

```text
原始资料
→ ETL / parser
→ staging / review / approval
→ 正式 SQLite
→ workbench 数据包 / 预览资源
→ 发布种子库和压缩包
```

顾问端流程：

```text
解压压缩包
→ 一键初始化
→ 浏览 / 搜索 / 查看关系 / 导出
```

两条流程必须分开设计。顾问端不应承担内部维护流程。

## 8. 后续升级原则

后续发布新版本时，应通过 manifest 比较应用版本、数据版本和资源 hash。

升级流程建议优先保证：

- 旧运行库先备份；
- 新种子库和资源经过 hash 校验；
- 用户本地导出、收藏、偏好和后续可能出现的备注不被静默覆盖；
- 升级失败可以回滚到上一版运行库。

第一期如果没有用户个人数据，可以把升级策略先做简单，但文档和目录结构应预留版本检查和备份位置。
