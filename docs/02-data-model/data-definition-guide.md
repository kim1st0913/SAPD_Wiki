# 数据定义与 ETL 设计指南

这份文档给非开发背景的项目负责人使用。目标不是让你先学数据库，而是帮助你从现有 Excel、DOCX、PPT、Draw.io 等资料中，逐步整理出系统需要的字段、知识对象、映射规则和更新流程。

## 1. 为什么开发前必须先做这件事

如果直接开始开发，系统很容易变成“能上传文件、能预览文件”的工具，但真正的知识库价值不在这里。

真正重要的是回答这些问题：

- 文件里哪些内容值得变成知识条目？
- 不同文件里反复出现的概念是不是同一个东西？
- 一个 Excel 列、一个 DOCX 章节、一个 PPT 页面、一个 Draw.io 节点，应该映射到哪个统一字段？
- 文件更新后，哪些数据应该新增、哪些应该修改、哪些要进入人工审核？
- 用户最终想按什么维度查询和导出？

所以开发前要先完成：

```text
知识资产盘点 → 知识对象识别 → 字段字典 → 字段映射 → ETL 规则 → 更新规则 → 数据库设计
```

## 2. 先不要从“数据库表”开始

非开发人员不需要一开始定义数据库表。更自然的顺序是：

1. 我有哪些文件？
2. 这些文件解决什么工作问题？
3. 我未来想怎么搜索、筛选、关联和导出？
4. 文件里反复出现哪些业务概念？
5. 这些业务概念需要哪些字段描述？
6. 字段稳定后，再交给 Codex 转成数据库表。

## 3. 第一阶段：知识资产盘点

先选少量最典型文件，不要一次性处理全部资料。

建议第一批：

- 3 到 5 个 Excel；
- 2 到 3 个 DOCX 或 Markdown；
- 1 到 2 个 PPT；
- 1 个 Draw.io。

每个文件只需要先回答：

| 问题 | 示例 |
|---|---|
| 这个文件叫什么？ | 安全能力矩阵.xlsx |
| 文件类型是什么？ | Excel |
| 它主要记录什么？ | 安全能力、控制项、成熟度 |
| 所属主题是什么？ | 零信任、安全架构、成熟度评估 |
| 内容类型是什么？ | 方法论、能力清单、流程、架构图、指标 |
| 是否结构化？ | 是 / 否 / 部分 |
| 是否可直接导入？ | 是 / 否 / 需清洗 |
| 谁会用它？ | 咨询顾问、售前、项目经理 |
| 最常查什么？ | 某个能力项、某类控制、某个项目适用性 |
| 最常导出什么？ | 能力清单、差距分析表、专题包 |
| 关联对象有哪些？ | 控制措施、系统组件、流程节点 |
| 更新频率？ | 高频 / 中频 / 低频 |
| 重要程度？ | 高 / 中 / 低 |
| 哪些内容应该结构化？ | 能力名称、说明、分类、等级、来源 |
| 哪些内容只需要作为附件保留？ | 说明截图、格式化版原表 |

## 4. 第二阶段：从文件中识别知识对象

知识对象是系统真正管理的东西，不等同于文件。

一个文件里可能包含多个知识对象。例如：

| 文件内容 | 可能抽取出的知识对象 |
|---|---|
| Excel 每一行 | 能力项、指标、控制措施、案例 |
| DOCX 每个章节 | 方法论、流程、要求、定义 |
| PPT 每页 | 观点、模型、案例、图示说明 |
| Draw.io 节点 | 系统、组件、接口、流程步骤 |
| Draw.io 连线 | 依赖关系、调用关系、流程关系 |

第一批建议只选 3 到 5 类知识对象：

- 方法论；
- 能力项；
- 控制措施；
- 风险项；
- 流程步骤；
- 指标；
- 案例；
- 架构元素；
- 术语。

不要一开始定义太多类型。类型太多会让导入和页面都变复杂。

## 5. 第三阶段：定义字段

字段不是从技术里来的，而是从“未来怎么用”里来的。

每个字段都要回答：

| 问题 | 说明 |
|---|---|
| 字段叫什么？ | 例如：能力名称 |
| 字段解决什么问题？ | 用来搜索、筛选、展示还是导出 |
| 字段是否必填？ | 没有这个字段是否还能入库 |
| 字段来自哪里？ | Excel 列、DOCX 标题、PPT 标题、人工填写 |
| 字段是否允许多个值？ | 例如标签、适用行业 |
| 字段是否需要标准化？ | 例如高/中/低、L1/L2/L3 |
| 字段冲突怎么办？ | 人工优先、来源优先、进入待审核 |

建议所有知识对象都先拥有一组通用字段：

| 字段 | 含义 |
|---|---|
| `title` | 标题或名称 |
| `type` | 知识类型 |
| `summary` | 摘要 |
| `content` | 正文或详细说明 |
| `category` | 分类 |
| `tags` | 标签 |
| `status` | 草稿、已发布、废弃 |
| `source_file` | 来源文件 |
| `source_location` | 文件内位置 |
| `owner` | 维护人或责任人 |
| `version` | 版本 |

然后每类知识对象再增加专属字段。例如“能力项”：

| 字段 | 含义 |
|---|---|
| `capability_domain` | 能力域 |
| `maturity_level` | 成熟度等级 |
| `applicable_scenario` | 适用场景 |
| `control_objective` | 控制目标 |
| `evidence` | 证据或参考资料 |

## 6. 第四阶段：设计来源映射

映射就是说明“来源文件的某个位置，进入系统后变成哪个字段”。

例如 Excel：

| 来源文件 | Sheet | 来源列 | 目标对象 | 目标字段 | 处理规则 |
|---|---|---|---|---|---|
| 安全能力矩阵.xlsx | 能力清单 | 能力名称 | 能力项 | `title` | 去掉前后空格 |
| 安全能力矩阵.xlsx | 能力清单 | 一级分类 | 能力项 | `category` | 映射到标准分类 |
| 安全能力矩阵.xlsx | 能力清单 | 标签 | 能力项 | `tags` | 按逗号拆分 |
| 安全能力矩阵.xlsx | 能力清单 | 成熟度 | 能力项 | `maturity_level` | 标准化为 L1-L5 |

例如 DOCX：

| 来源位置 | 目标对象 | 目标字段 | 处理规则 |
|---|---|---|---|
| 一级标题 | 方法论 | `title` | 作为知识标题 |
| 标题下段落 | 方法论 | `content` | 合并为正文 |
| 表格第一列 | 控制措施 | `title` | 每行生成一个控制措施 |
| 表格第二列 | 控制措施 | `summary` | 作为摘要 |

例如 Draw.io：

| 来源元素 | 目标对象 | 目标字段 | 处理规则 |
|---|---|---|---|
| 节点文本 | 架构元素 | `title` | 每个节点生成一个元素 |
| 节点样式 | 架构元素 | `type` | 根据形状或泳道推断 |
| 连线 | 知识关系 | `relation_type` | 默认为“关联”或“依赖” |
| 连线标签 | 知识关系 | `note` | 保存关系说明 |

## 7. 第五阶段：设计 ETL 流程

ETL 可以理解为“把文件变成数据库记录”的流水线。

建议流程：

```text
Extract 提取
→ Normalize 清洗标准化
→ Map 映射到统一字段
→ Validate 校验
→ Stage 进入暂存区
→ Review 人工审查
→ Load 正式入库
→ Log 记录变更
```

每一步的作用：

| 步骤 | 作用 | 示例 |
|---|---|---|
| Extract | 从文件读取内容 | 读取 Excel 行、DOCX 标题、PPT 页 |
| Normalize | 清理格式 | 去空格、统一日期、拆分标签 |
| Map | 映射字段 | Excel 的“能力名称”映射到 `title` |
| Validate | 检查规则 | 必填字段不能为空 |
| Stage | 暂存 | 先进入导入预览，不直接覆盖 |
| Review | 审查 | 用户确认新增、修改、冲突 |
| Load | 入库 | 写入正式知识表 |
| Log | 记录 | 写入 import_job 和 change_log |

## 8. 第六阶段：设计更新规则

更新机制比首次导入更重要。建议按来源和优先级处理。

| 场景 | 建议规则 |
|---|---|
| 第一次导入文件 | 生成新来源和新知识条目 |
| 同一个文件重新导入 | 根据文件 hash 判断是否变化 |
| 同一条知识字段变化 | 生成 diff，进入待审核 |
| 自动 ETL 与人工编辑冲突 | 人工编辑优先 |
| 第三方文件导入 | 默认进入待审核 |
| 找到重复知识 | 提供合并建议，不自动合并 |
| 来源文件删除 | 标记来源失效，不直接删除知识 |

## 9. 用户与 Codex 的配合方式

你不需要一次性想清楚所有字段。可以这样推进：

1. 你给 Codex 3 到 5 个样例文件。
2. Codex 先做样例文件盘点。
3. Codex 提取候选知识对象和候选字段。
4. 你确认哪些对象和字段真的有用。
5. Codex 生成字段字典和映射表。
6. Codex 设计数据库表。
7. Codex 实现最小导入程序。
8. 你用真实文件试导入。
9. Codex 根据试导入结果修正规则。

一句话：你负责判断“业务上有没有用”，Codex 负责把它整理成字段、规则和代码。

## 10. 开发前检查清单

正式写代码前，至少完成：

- [ ] 第一批样例文件清单；
- [ ] 第一批知识对象类型；
- [ ] 通用字段定义；
- [ ] 至少一种文件类型的映射规则；
- [ ] 必填字段和校验规则；
- [ ] 更新和冲突处理规则；
- [ ] 哪些文件能进 GitHub，哪些必须本地保存；
- [ ] 一个最小导入闭环的验收标准。

## 11. 推荐输出物

前期可以先用 Markdown 表格维护，等样例稳定后再生成 Excel 配置表。

| 输出物 | 作用 |
|---|---|
| `knowledge_asset_inventory.xlsx` | 知识资产盘点表 |
| `knowledge_objects.xlsx` | 知识对象定义表 |
| `field_dictionary.xlsx` | 字段字典表 |
| `mapping_rules.xlsx` | 字段映射规则表 |
