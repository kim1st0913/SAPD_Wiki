# SAPD Wiki 前端信息架构方案

本文档是 Frontend Design Owner 对 SAPD Wiki 下一轮前端重构的信息架构方案。它承接 `frontend-redesign-brief.md`、前端优化建议和 `OI-018` 至 `OI-022` 的修正方向，只定义页面、视图模式、交互结构和数据契约，不涉及本轮代码实现。

前后端分离后的字段级数据契约以 `docs/01-architecture/api-field-contract.md` 为准；本文档只定义前端页面结构、信息组织和交互方式。

## 1. 设计结论

SAPD Wiki 前端应从“资料展示页”转为“业务关系工作台”。

核心修正：

- 前端主入口不再围绕“某条记录来自哪个 Sheet、哪一行、哪个字段”组织。
- 来源追踪仍然保留，但降为导入审查、数据质量排查和主动展开的证据能力；常规业务页面默认不展示来源字段。
- 第一层页面以业务关系维度组织：能力、信息化环境、安全开发、数据生命周期、专项维护、说明与视图。
- 主视图优先使用树表、矩阵、关系链、泳道、分组清单和局部关系图。
- 卡片只可作为少量摘要块或详情中的辅助表达，不作为一级页面主要形态。

这意味着当前 `知识来源` 模块在下一轮应被重新命名和重构为 `专项知识维护`。它不是让用户“按来源看数据”，而是让用户维护作用域、流程、职能、模块、标准和岗位这些业务主数据。

## 4. 前后端分离后的数据接入方式

前端不直接理解原始 Excel，也不负责业务关系推断。前端只通过 `dataClient` 消费后端投影或当前静态 JSON。

```text
当前 MVP：
public/data/*.json
→ dataClient
→ 页面组件

后续本地 API：
/api/v1/*
→ dataClient
→ 页面组件
```

设计要求：

- `dataClient` 是页面组件唯一数据入口。
- 页面组件不直接散落 `fetch` 多个 JSON 文件。
- 页面组件不根据 `sources`、Sheet、row、column、raw_value 推断业务关系。
- 能力矩阵、环境矩阵、专项清单、生命周期关系优先使用后端投影字段。
- 新增字段先更新 `docs/01-architecture/api-field-contract.md`，再更新导出脚本和前端。

## 5. 来源追踪的正确位置

来源追踪不是前端主导航，也不是业务页面的第一组织维度。

正确放置方式：

| 场景 | 显示方式 | 说明 |
|---|---|---|
| 导入审查 | 来源证据区 | 展示 Sheet、行、列、单元格、raw_value |
| 数据质量排查 | 问题详情中的证据区 | 支撑主控或 ETL 判断 |
| 对象详情调试模式 | 折叠区，默认关闭 | 仅排查问题时打开 |
| 关系详情调试模式 | 折叠区，默认关闭 | 仅排查关系生成问题时打开 |
| 导入审计 | 独立治理页面，后置 | 不进入当前业务关系首页 |

页面标题、导航和筛选项不应使用 `知识来源`、`Sheet`、`行号` 作为主要概念。面向用户的主概念应是 `能力`、`信息化对象`、`作用域`、`流程`、`职能`、`技术模块`、`生命周期`、`标准`、`岗位`。

## 6. UI 模式规范

### 6.1 禁止作为主模式

- 卡片墙。
- 营销式首页。
- 只展示标题、摘要、标签的资料列表。
- 用大量 chip 代替真实关系。
- 把关系塞进不可比较的卡片详情。

### 6.2 推荐模式

| 模式 | 适用页面 | 结构 |
|---|---|---|
| 树表 | 能力树、流程清单、应用类型字典 | 层级列 + 编码 + 名称 + 数量 + 状态 |
| 映射矩阵 | 能力-服务-作用域、环境覆盖、LC-DT 过程矩阵 | 行为主对象，列为关系维度，单元格展示覆盖或数量 |
| 关系链 | 环境对象链、能力-模块链、过程-服务-模块 | `对象 -> 作用域 -> 服务 -> 模块 -> 系统/产品` |
| 生命周期泳道 | LC-AP、LC-DT 总览 | 阶段/过程横向排列，活动、策略、服务在泳道内分层 |
| 分组清单 | 职能、标准、岗位、说明目录 | 按层级或主题分组，支持快速扫描 |
| 局部关系图 | 关系总览、对象详情 | 只展示当前对象一跳或两跳关系，不做全量图谱 |
| 类 Excel 表格 | 作用域清单、安全技术模块清单 | 贴近原始表核对习惯，支持搜索和行详情 |

### 6.3 标准页面布局

关系型页面采用三栏工作台：

```text
左侧：维度树 / 分组导航 / 筛选
中间：主表 / 矩阵 / 泳道
右侧：当前对象或关系详情
```

专项维护页面采用：

```text
左侧：专项二级页面导航
中间：可核对清单或类 Excel 表
右侧：实体详情 + 关联信息；来源证据仅在调试/审查模式展开
```

说明与视图页面采用：

```text
左侧：文档 / 图 / 幻灯片目录
中间：正文阅读或图预览
右侧：元数据、相关业务对象；来源文件仅作为后置证据
```

## 7. 专项知识维护页定义

专项维护页是基础业务字典和关系核对区，不是来源文件浏览器。

| 页面 | 维护对象 | 必须展示字段 | 关系展示 |
|---|---|---|---|
| 作用域清单 | `scope_type` | 情景、作用域编码、作用域类型、描述 | 关联服务、关联信息化对象 |
| 流程清单 | `process_domain`、`process_group`、`process_reference`、未来 `process_activity` | 流程域、L2 流程组、L3 流程、L4 活动状态、描述 | 关联关注点、关联职能 |
| 职能清单 | `work_function_layer`、`work_function_group`、`work_function` | 职能层、职能组、职能编码、职能名称、定义 | 关联任务、GB/T 参考、流程相关方 |
| 安全技术模块清单 | `security_technology_module`、`security_system`、`product` | 分类、系统、模块、服务数、产品数、环境数 | 关联服务、系统、产品、环境 |
| 标准与岗位参考 | `gbt_42446_task_reference`、`work_role_reference` | 标准分类、任务名称、岗位分类、岗位名称、说明 | 关联职能，后续可关联流程 |

当前 `OI-019` 要求作用域清单按原始表格样式展示，应保留 `情景 / 作用域类型 / 描述` 的表格核对体验。来源字段不在默认表格中展示。

当前 `OI-021` 要求能力详情中流程与组织职能相关方不能重复显示。流程相关视图应固定展示：

```text
L2 流程组
└── L3 流程
    ├── L4 关键活动：有值则展示；无值显示“待补充”
    └── 组织职能相关方：决策层 / 管理层 / 执行层 / 监督层
```

## 8. 非表格内容接入方式

### 8.1 HTML 知识说明

用途：

- 展示知识库使用说明。
- 展示方法说明、页面说明、导入说明。
- 承载由 Markdown、DOCX 或人工 HTML 转换来的阅读型内容。

接入方式：

- 前端新增 `说明与视图 > HTML 知识说明`。
- ETL 或构建脚本输出一个说明目录 JSON，例如 `content-views.json` 中的 `html_documents`。
- 每个文档保留 `id`、`title`、`category`、`html_path` 或 `content_html`、`source_file_id`、`updated_at`。
- 文档正文不与业务关系页面混排；只在相关对象详情中提供“相关说明”链接。

### 8.2 Draw.io 只读图

用途：

- 展示元模型、技术架构、流程图、功能架构图。
- 第一阶段只读，不做在线编辑。
- 不强制把图节点自动关联到 Excel 对象，先保留手工或后续 ETL 关联能力。

接入方式：

- 前端新增 `说明与视图 > Draw.io 只读图`。
- 后端或预处理脚本输出 `diagram_views`。
- 每个视图包含 `id`、`title`、`page_index`、`view_type`、`preview_path`、`drawio_path`、`vertex_count`、`edge_count`、`source_file_id`。
- 主视图显示图预览；右侧显示页面元数据、节点/连线数量和可选关联业务对象。

### 8.3 PPT 使用说明

用途：

- 展示 `wiki sample ppt.pptx` 或后续 PPT 中的使用说明、方法论、页面说明。
- 第一阶段按页级或章节级阅读，不追求原 PPT 复杂版式完全还原。

接入方式：

- 前端新增 `说明与视图 > PPT 使用说明`。
- ETL 或转换脚本输出 `guide_pages`。
- 每页包含 `id`、`slide_number`、`title`、`content`、`note`、`preview_path`、`media_count`、`source_file_id`。
- 页面左侧为幻灯片目录，中间为页正文或预览，右侧为来源与相关业务对象。

## 9. 下一轮实现顺序与数据契约

字段级契约以 `docs/01-architecture/api-field-contract.md` 为准。前端实现顺序应先建立 `dataClient`，再扩展页面。

### Step 1：建立关系化导航与页面骨架

目标：

- 把顶层导航改为本文档定义的 7 个一级页面。
- 将现有 `知识来源` 入口重命名为 `专项知识维护`。
- 保留现有数据加载方式，先不引入复杂框架。

数据契约：

- 可继续读取 `capability-tree.json`。
- 可继续读取 `management-knowledge.json`。
- 需要前端本地维护一份页面配置，或由 ETL 后续导出 `frontend-navigation.json`。
- 通过 `dataClient` 读取，不在页面组件中散落直接 `fetch`。

主控/ETL 需确认：

- 一级页面中文命名是否固定。
- `知识来源` 是否正式退出顶层导航命名。

### Step 2：重构能力维度

目标：

- 保留能力树，但把详情页从“来源追踪优先”改为“关系工作台”。
- 增加能力-服务-作用域矩阵和能力-流程-职能矩阵。
- 关系详情默认展示业务关系；来源证据只在调试/审查模式下折叠展示。

当前可用数据：

- `capability-tree.json.categories[].domains[].capabilities[].focuses[]`
- `focus.services[]`
- `focus.security_works[]`
- `focus.process_mappings[]`
- `process_mappings[].process_group`
- `process_mappings[].process_reference`
- `process_mappings[].activities`
- `process_mappings[].stakeholders`

需要补充或确认的数据契约：

- `focus.scope_mappings` 或等价的关注点到作用域汇总，避免前端只能从服务反推。
- `service.modules`、`service.systems`、`service.products` 或独立 `service_module_index`，用于能力-模块关系链。
- L4 关键活动为空时继续使用 `待补充`，还是由 ETL 输出显式 `missing` 状态。

### Step 3：强化信息化环境维度

目标：

- 将当前 `信息化对象` 页面升级为完整 `信息化环境维度`。
- 主视图展示 `信息化环境 -> 信息化对象 -> 作用域 -> 服务 -> 模块 -> 系统/产品`。
- 增加环境覆盖矩阵，便于横向核对。

当前可用数据：

- `management-knowledge.json.environment_scope_tree[]`
- `environment.objects[]`
- `object.scope_mappings[]`
- `scope_mappings[].services[]`
- `services[].modules[]`
- `modules[].systems[]`
- `modules[].products[]`

需要补充或确认的数据契约：

- 信息化环境、对象、作用域、服务、模块的排序字段。
- `environment_segment` 是否仍作为单独层级展示，还是合并进信息化对象。
- 覆盖矩阵的单元格显示口径：数量、名称摘要，还是覆盖状态。

### Step 4：整理专项知识维护

目标：

- 将作用域、流程、职能、技术模块、标准与岗位参考统一到 `专项知识维护`。
- 页面主形态改为表格、树表和分组清单。
- 默认不展示来源列；需要核对原始数据时通过调试/审查模式查看来源证据。

当前可用数据：

- `management-knowledge.json.scope_types[]`
- `management-knowledge.json.security_processes[]`
- `management-knowledge.json.work_function_layers[]`
- `management-knowledge.json.security_technology_modules[]`
- `management-knowledge.json.gbt_42446_references[]`
- `management-knowledge.json.gartner_roles[]`

需要补充或确认的数据契约：

- 每类专项对象的稳定排序字段。
- 模块清单中数字型或疑似异常标题的处理口径由主控/ETL确认。
- 标准参考与岗位参考是否需要生成到职能、流程的正式关系。

### Step 5：接入安全开发维度

目标：

- 新增 `安全开发维度` 页面。
- 用 LC-AP 生命周期泳道展示阶段、主要活动、安全活动、策略、开发技术服务和产品示例。
- 用字典页展示软件开发类型、应用系统类型、应用组件。

需要新增数据契约：

建议新增 `lifecycle-knowledge.json`：

```json
{
  "generated_at": "string",
```

## 10. 验收标准

下一轮前端实现完成后，应按以下标准验收：

- 顶层导航体现业务维度，不再以 `知识来源` 作为核心入口。
- 能力维度能清楚看到能力、关注点、服务、作用域、流程、职能、模块之间的关系。
- 信息化环境维度能清楚看到环境、对象、作用域、服务、模块、系统/产品的连续映射。
- 专项知识维护页覆盖作用域清单、流程清单、职能清单、安全技术模块清单、标准与岗位参考。
- 安全开发维度和数据生命周期维度即使暂未接入数据，也有明确页面位置和数据契约。
- HTML 知识说明、Draw.io 只读图、PPT 使用说明有明确入口和接入方式。
- 来源追踪默认不展示；只在导入审查、数据质量排查或调试模式中查看。
- 主要页面不出现卡片墙。
