# 全局搜索重设计方案

> 归档状态：`retired / superseded design`。当前完整搜索规则以
> `docs/06-implementation/global-search-contract-2026-07-05.md` 为准。

日期：2026-06-30

关联问题：`OI-155`、`OI-154`、`OI-149`、`OI-144`

最新同步设计入口：`docs/06-implementation/search-governance-oi154-oi155-synchronized-design-2026-07-02.md`。后续实现以该文档拆分 `OI-155` 全局搜索和 `OI-154` 页面内搜索边界；本文保留全局搜索产品形态基础方案。

## 设计结论

SAPD Wiki 不适合只保留一个全局搜索框，也不适合继续保留现在这种“顶部全局搜索 + 多个看起来一样的页面搜索”。

最佳实现方式是：

1. 顶部保留一个全局搜索入口，用于跨知识域查找和导航。
2. 新增独立搜索结果页 `#/search?q=...`，作为全局检索的主要工作区。
3. 页面内搜索继续保留，但只作为当前模块、当前树、当前表格、当前映射图的局部查找或筛选工具。
4. 全局搜索使用轻量 `search-index`，不得为了输入一个关键词加载完整 workbench、完整字典、完整标准详情或环境全量包。

也就是说：全局搜索负责“找到在哪里”，页面内搜索负责“在当前上下文里筛选和定位”。

## 为什么选择这个方案

### 不选择“只有一个全局搜索框”

SAPD Wiki 是安全架构关系审查工作台，不是普通文档站。用户经常需要在当前环境对象、当前标准表、当前能力关系、当前生命周期阶段里快速筛选。如果只保留一个全局搜索框，用户每次都要离开当前上下文进入搜索结果页，再跳回来，审查效率会下降。

### 不选择“继续保留所有现状搜索”

现状的问题不是搜索框数量，而是职责混杂：

- 顶部全局搜索承担跨域搜索、页面过滤、定位高亮和数据预热。
- 页面搜索看起来像全局搜索，但实际只影响局部视图。
- 全局搜索输入会触发多个大 JSON 包加载，放大 `OI-149` 慢加载问题。
- 全局搜索结果点击后又把搜索词传给目标页，容易再次制造 `OI-144` 状态串线问题。
- 环境页等新页面的局部搜索未形成统一契约，导致用户反馈“环境页下面的搜索无法使用”。

继续在现状上补丁，会让搜索、定位、批注锚点和 JSON 加载继续互相牵连。

### 推荐的产品形态

采用“全局搜索 + 搜索结果页 + 模块内局部查找”的三层模型：

| 层级 | 用户意图 | UI 形态 | 数据来源 |
|---|---|---|---|
| 顶部全局搜索 | 跨域查找一个对象、标准、服务、模块、环境或页面 | 顶部搜索框 + 轻量结果面板 | `search-index` |
| 搜索结果页 | 系统性查看、过滤和打开全局搜索结果 | `#/search?q=...` 三栏或两栏结果工作区 | `search-index` + 按需 projection |
| 页面内搜索 | 在当前页面、当前树、当前表格或当前映射图里筛选 | 面板内搜索框 / 字段过滤 | 当前页面已加载 projection |

## 搜索信息架构

### 顶部全局搜索

顶部搜索框只做全局检索入口。

推荐行为：

- 输入 1 个以上有效字符后打开轻量结果面板。
- 面板只展示前 6-8 条高置信结果。
- 面板底部提供 `查看全部结果`，进入 `#/search?q=关键词`。
- 按 `Enter` 默认进入搜索结果页，而不是直接跳第一个结果。
- 支持键盘上下选择结果，按 `Esc` 关闭面板。
- 搜索框不写入页面内搜索状态。
- 搜索框不驱动当前页面过滤。

顶部轻量结果面板应该是“快速入口”，不是完整结果页。

### 搜索结果页

新增 `#/search?q=...` 作为全局搜索主界面。

推荐布局：

- 左侧：结果类型和范围筛选。
- 中间：结果列表。
- 右侧或列表内展开：结果摘要、路径和操作。

结果页应支持的筛选：

| 筛选 | 示例 |
---|---|
| 类型 | 能力、关注点、环境对象、安全技术服务、安全技术模块、安全技术措施、安全系统、标准控制项、生命周期阶段、指南内容、用户批注 |
| 知识域 | 安全能力、信息化环境、LC-AP、LC-DT、知识库字典、标准 / 框架、指南 |
| 匹配字段 | 标题、编码、别名、路径、正文摘要 |
| 是否可定位 | 可直接定位、只能打开页面、需要加载详情 |

结果项推荐字段：

| 字段 | 说明 |
---|---|
| 标题 | 用户可读业务标题 |
| 编码 | 如 `I-AP&T-AS.AD-01`、`AP-01`、标准控制编号 |
| 类型标签 | 安全技术服务 / 标准控制项 / 环境对象等 |
| 所属路径 | 例如 `信息化环境 / 云数据中心 / 业务应用 / API网关层` |
| 命中摘要 | 高亮命中的标题、编码或上下文短句 |
| 操作 | `打开`、`定位` |
| 加载状态 | 目标详情未加载时显示 `打开后加载详情` |

结果页的核心价值是让用户判断“这个结果属于哪个业务上下文”，而不是只给一串文字命中。

### 页面内搜索

页面内搜索保留，但必须改成明确的局部工具。

命名建议：

| 页面 | 不建议 | 建议 |
---|---|---|
| 信息化环境页 | `搜索` | `筛选环境、对象、服务或模块` |
| 安全能力页 | `搜索` | `查找当前能力关系` |
| 标准 / 框架页 | `搜索` | `筛选当前标准控制项` |
| 字典页 | `搜索` | `筛选当前目录` |
| LC-AP / LC-DT | `搜索` | `查找阶段内容` |

页面内搜索规则：

- 只影响当前页面或当前面板。
- 不进入全局搜索历史。
- 不改变顶部全局搜索框。
- 不触发全局 `search-index` 之外的大包加载。
- 无结果时显示“未找到匹配项”，不能显示数据包缺失。
- 对树、表格、图节点要有明确作用域：过滤列表、展开节点、定位首个命中，三者不能混在一起不说明。

## 数据与性能设计

### search-index 是全局搜索的唯一首选数据源

全局搜索输入阶段只允许加载轻量 `search-index`。不得直接加载：

- `environment-workbench.json`
- `capability-workbench.json`
- `maintenance-knowledge.json`
- `lifecycle-knowledge.json`
- `lifecycle-workbench.json`
- standards 详情分片全表
- 指南 / 幻灯片完整正文包

`search-index` 建议字段：

```json
{
  "id": "security_technical_service:I-AP&T-AS.AD-01",
  "type": "security_technical_service",
  "typeLabel": "安全技术服务",
  "domain": "maintenance",
  "title": "应用架构管控",
  "code": "I-AP&T-AS.AD-01",
  "path": ["知识库字典", "安全技术服务清单", "I-AP 软件应用"],
  "route": "/knowledge/technical-services",
  "targetRef": "security_technical_service:I-AP&T-AS.AD-01",
  "targetText": "I-AP&T-AS.AD-01 应用架构管控",
  "keywords": ["应用架构管控", "AD-01", "架构", "管控"],
  "summary": "I-AP 软件应用下的安全技术服务"
}
```

字段边界：

- 不写入 `sheet`、`row`、`column`、`raw_value`、`source_file`、`generated_at`、`debug`、`metadata`。
- 来源证据不进入主结果，只能在目标详情页的折叠证据区查看。
- 用户批注不进入静态 `search-index`；如要搜索批注，应通过本地用户 API 单独取数，并作为结果页的一个可选类型。

### 搜索匹配与排序

推荐排序权重：

1. 编码精确匹配，例如 `I-AP&T-AS.AD-01`。
2. 标题精确匹配。
3. 编码前缀匹配，例如 `AD-01`。
4. 标题包含匹配。
5. 路径 / 所属上下文匹配。
6. 摘要 / keywords 匹配。

同分排序建议：

1. 当前页面相关结果优先，但不能只显示当前页面。
2. 业务主对象优先于辅助文本。
3. 标题 / 编码命中优先于摘要命中。
4. 可定位结果优先于只能打开页面的结果。

中文搜索建议：

- 第一版先做大小写归一、空格归一、全角半角归一、标点归一。
- 编码搜索必须保留 `-`、`&`、`.` 等符号的原始匹配能力。
- 暂不引入复杂分词或拼音，避免引入重依赖和不可解释排序。

### 加载预算

建议预算：

| 场景 | 预算 |
---|---:|
| 首次输入全局搜索 | 只加载 `search-index`，目标小于 `800 KB` |
| 顶部轻量面板渲染 | 结果不超过 8 条 |
| 搜索结果页首屏 | 首屏 JSON 小于 `1 MB` |
| 点击结果定位 | 只加载目标页面 projection 或目标分片 |
| 页面内搜索 | 不触发任何全局大包加载 |

## 交互状态设计

### 状态分离

必须保留三个独立状态：

| 状态 | 用途 |
---|---|
| `globalSearch.query` | 顶部全局搜索输入 |
| `searchPage.query` | `#/search` 结果页查询，由 URL 驱动 |
| `pageSearches[scope]` | 页面内局部搜索和过滤 |

禁止：

- 全局搜索自动写入 `pageSearches`。
- 页面内搜索自动写入 `globalSearch`。
- 搜索结果点击后把关键词强行灌入目标页搜索框。

允许：

- 搜索结果点击后带 `targetRef` 进入目标页。
- 目标页按 `targetRef` 定位具体业务锚点。
- 如果目标页没有该锚点，显示“已打开目标页面，未找到可定位锚点”。

### 结果点击策略

结果点击分两步：

1. 路由到目标页面或目标结果页。
2. 目标页面加载完成后，用 `targetRef` 定位业务锚点。

如果定位失败：

- 不反复全 DOM 扫描。
- 不把关键词写入页面内搜索框当作兜底。
- 只允许一次轻量文本 fallback。
- 失败后给出状态：`已打开页面，未能定位到具体项`。

## 结果类型覆盖

第一阶段应覆盖：

- 页面导航项。
- 安全能力、关注点。
- 安全技术服务。
- 安全技术模块。
- 安全技术措施。
- 安全系统。
- 信息化环境、环境子类、信息化对象。
- LC-AP 阶段和关键业务单元。
- LC-DT 过程和关键业务单元。
- 标准 / 框架、标准控制项。
- 知识库字典目录和主要条目。

第二阶段再覆盖：

- 指南 / 幻灯片正文摘要。
- 用户批注。
- 用户收藏。
- 导出数据集。

## 实施路线

### P0：设计与防线

- 登记 `OI-155`。
- 将本方案作为全局搜索主设计文档。
- 在 `search-logic-design.md` 中标明旧文档只保留状态隔离原则，新全局搜索形态以本方案为准。
- 增加审计计划：顶部全局搜索不得写页面搜索，页面搜索不得写全局搜索。

### P1：全局搜索结果页骨架

- 新增 `#/search?q=...` 页面。
- 顶部全局搜索按 `Enter` 进入结果页。
- 轻量面板只显示 top results 和 `查看全部结果`。
- 不在本阶段重建正式 JSON。

### P2：search-index 契约

- 新增 `search-index` 生成器或 API。
- 建立 `audit_global_search_index_contract`：
  - 搜索输入阶段不加载全量 workbench。
  - 索引字段不泄露 raw/source/debug 字段。
  - 结果类型覆盖核心知识域。

### P3：页面内搜索治理

- 新增 `OI-154` 页面内搜索回归治理。
- 环境页优先修复：树搜索、对象搜索、服务 / 模块 / 措施 / 系统搜索。
- 页面内搜索改用当前 projection，不读取全局索引。
- 页面内搜索无结果统一显示局部空态。

### P4：结果定位与锚点验收

- 搜索结果点击使用 `targetRef` 定位。
- 每个核心页面声明可定位对象类型。
- 定位失败要可解释，不再多轮重试拖慢页面。

## 验收标准

功能验收：

- 顶部搜索输入不会改变任何页面内搜索框。
- 页面内搜索输入不会改变顶部搜索框。
- 顶部搜索按 `Enter` 进入 `#/search?q=...`。
- 搜索结果页能按类型和知识域筛选。
- 搜索结果点击后能打开目标页面，并尽可能定位到业务锚点。
- 环境页局部搜索能筛选或定位环境、对象、服务、模块、措施、安全系统。

性能验收：

- 全局搜索首字输入不加载 `environment-workbench.json`、`capability-workbench.json`、`maintenance-knowledge.json`、`lifecycle-workbench.json` 或标准详情全表。
- `search-index` 小于 `800 KB`，超出时按领域拆分。
- 页面内搜索不触发全局数据包加载。

字段边界验收：

- 全局搜索结果和搜索索引不展示或包含 `sheet`、`row`、`column`、`raw_value`、`source_file`、`import_id`、`source_id`、`source_ref`、`source_label`、`debug`、`raw`、`metadata`、`intermediate`、`generated_at`。

回归验收：

- `audit_search_state_isolation.mjs`
- `audit_global_search_index_contract.mjs`
- `audit_environment_search_contract.mjs`
- `audit_frontend_lazy_load_contract.mjs`
- `frontend_content_smoke_check.mjs --skip-api`

真实浏览器验收需用户明确批准后执行。

## 回退策略

- `OI-155` 的 UI 形态改造必须独立提交，不能和 `OI-149` 加载治理混在一个提交里。
- 搜索结果页可通过路由入口回退，不影响现有页面渲染。
- `search-index` 可先作为新增包，不替换现有数据包。
- 页面内搜索治理必须逐页提交，环境页搜索修复不能同时改标准页、字典页和生命周期页。
- 如果新搜索结果页失败，顶部搜索可以临时回退到轻量面板，但不能恢复全量 JSON 预热。

## 最终建议

先确认 `OI-155` 设计，再开始写代码。实施时优先顺序为：

1. 先做 `OI-149 P0`，切断全局搜索大包预热。
2. 再做 `OI-155 P1`，增加搜索结果页骨架和全局搜索入口改造。
3. 再做 `OI-149 P1`，生成 `search-index`。
4. 再做 `OI-154`，治理环境页和其他页面内搜索。

这样可以避免再次出现“为了修搜索，顺手改加载；为了修加载，顺手改定位；最后前后端一起乱”的问题。
