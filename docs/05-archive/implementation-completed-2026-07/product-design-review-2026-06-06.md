## 总体结论

当前前端已经明显优于泛化 Apple dashboard 方案。它的价值不在“视觉惊艳”，而在已经形成了适合本项目的业务工作台结构：左侧全局模块、顶部搜索、页面级标题、业务树 / 阶段条 / 拓扑图 / 矩阵表、右侧批注层。这套结构应作为后续设计基线继续保留。

后续不建议做整体换壳或重新设计页面框架。更合理的方向是做局部设计系统加固：统一导航层级、统一矩阵密度、统一 chip 语义、统一批注抽屉与高亮状态，并解决深层路由直接访问掉样式的问题。

## 应保留的设计资产

1. **左侧全局导航已经成立**

当前导航不是普通菜单，而是项目的业务对象地图。安全能力、信息化环境、LC-AP、LC-DT、知识库字典、标准框架都能在一个稳定壳内切换。这个结构应保留，不要改成顶部横向大菜单或卡片入口。

2. **能力映射页的双栏结构是正确的**

`安全能力映射` 左侧能力树 + 右侧图谱 / 技术视角 / 管理视角 / 标准映射，是当前项目最核心的信息架构。它比单页 dashboard 更适合长期审阅。

3. **LC-AP / LC-DT 的阶段条很适合业务理解**

阶段条把生命周期页面从“表格堆叠”变成了“按业务阶段审阅”。这是当前前端最值得复用到后续专题页的模式。

4. **信息化环境拓扑页方向正确**

环境页的拓扑视图有清晰的业务空间感，比纯表格更适合表达环境 / 子类 / 对象 / 作用域的层级关系。后续应优化密度和阅读路径，而不是替换为普通表格页。

5. **批注抽屉已经进入可用状态**

右侧批注抽屉现在能承载页面级数量、添加批注、批注列表、状态、定位、编辑和删除。它应该继续作为全局批注基线，不建议再大改交互模型。

## 主要问题

### P0：深层路由直接访问未加载样式

证据：`07-guide-security-architecture-design.png`、`08-knowledge-technical.png`、`09-standards-iso-27001.png`。

直接访问 `/guides/security-architecture-design`、`/knowledge/technical`、`/standards/iso-27001-2022` 时，页面掉到未样式化状态，只剩原生 HTML。这个问题比视觉微调更重要，因为它会影响：

- 用户从浏览器地址栏、收藏夹、批注定位、外部链接进入页面；
- 后续导出或内部团队分发时的可信度；
- Product Design audit、截图验收和自动化回归的稳定性。

建议优先修复资源路径 / history fallback / base path，不要先继续改颜色或抽屉细节。

### P1：全局导航的层级表达不够稳定

左侧视觉上主要展示一级模块，但 DOM 中存在大量二级路由按钮。自动化和视觉状态出现不一致，说明导航层级的“可见 / 可点 / 当前展开”状态需要治理。

建议后续明确：

- 一级模块是否始终显示；
- 二级模块是否只在父级展开时显示；
- 当前路由属于二级页面时，父级和子级如何同时高亮；
- 隐藏的二级按钮是否应从交互树中移除，避免自动化和键盘用户误入。

### P1：批注抽屉展开后遮挡主工作区过多

证据：`03-capability-mapping-annotation-open.png`。

抽屉展开后右侧遮挡图谱，同时左侧仍保留大量主工作区内容。当前适合“临时查看批注”，但不适合长时间批注治理。

建议不要改变交互模型，只优化两件事：

- 打开抽屉时主内容区增加更明确的右侧安全边界，避免重要内容被半遮挡；
- 批注列表默认用更紧凑的行式列表，展开某条时再显示正文和操作。

### P2：首页统计卡片偏“数据包健康”，与用户工作流仍有距离

证据：`01-overview.png`。

首页信息清楚，但目前更像数据状态总览。用户进入系统的高频动作是找能力、看关系、定位依据、处理批注。首页可以保留统计，但应把入口语义从“对象 / 关系 / 来源数量”逐步转为“能力覆盖 / 待确认 / 有批注 / 最近查看 / 场景入口”。

这与新增的 `dashboard-and-module-data-display-optimization-design.md` 方向一致。

### P2：矩阵和 chip 的视觉层级还可以更克制

LC-AP / LC-DT 页面中，表格、chip、引用框、阶段条已经可用，但同屏语义层级较多。后续应统一：

- 服务 chip、模块 chip、标准 chip、状态 chip 的色彩规则；
- 值级批注高亮与 chip 原始语义色的叠加方式；
- 空值 `/`、参考来源、正文说明的低优先级样式。

## 可访问性风险

截图不能证明完整可访问性，只能指出可见风险：

1. 深层路由未加载样式时，页面虽然有原生控件，但整体阅读顺序和可用性明显下降。
2. 左侧导航二级入口的可见状态与交互状态可能不一致，键盘焦点和屏幕阅读器可能进入视觉上不可见的项目。
3. 图谱节点文字偏小，截图中难以阅读；需要后续用浏览器实际检查缩放、键盘导航和节点详情入口。
4. 批注抽屉打开后主内容被遮挡，需要确认焦点是否被限制在抽屉内，关闭后是否回到触发按钮或当前锚点。

## 后续建议顺序

1. **先修深层路由样式问题**

这是 P0。修完后再重新抓指南、知识库、标准页截图，否则这些页面无法做有效视觉审阅。

2. **固化当前前端设计基线**

不要换壳。把当前真实页面的设计资产整理成一份组件级规则：导航、页面头、阶段条、树、矩阵、chip、批注抽屉、普通高亮、定位高亮。

3. **做 CSS / 组件小步统一**

优先统一 chip、表格、抽屉列表和空值样式。不要同时改路由、数据契约和批注逻辑。

4. **再做首页工作流调整**

首页从数据包健康逐步转向工作入口，但不要做营销式大首页。

## 不建议

- 不建议继续用 ImageGen 生成整体前端替代方案。
- 不建议把当前项目改成泛化 Apple dashboard。
- 不建议大改 `app.js` / `styles.css` 结构来追求一次性视觉重构。
- 不建议在深层路由样式问题未修复前继续评审指南、知识库和标准页的视觉细节。
