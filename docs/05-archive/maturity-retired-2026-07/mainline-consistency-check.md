# 成熟度模型与主工程一致性核对草案

> 归档状态：历史一致性检查证据，不作为当前实现合同。

本文档记录 maturity 模块 M1 的第一轮只读一致性核对结果。核对对象为新版 `sample 评分表.xlsx` 抽取出的成熟度模型基准，以及主工程当前 active 状态的已治理知识对象。

本轮不做：

- 不修改主工程 schema；
- 不修改 `knowledge_items`；
- 不实现评分算法；
- 不生成前端页面；
- 不把安全技术服务作为独立成熟度评分对象。

## 1. 业务口径

业务逻辑来源：

- 模型设计严格参考 `sample文档介绍.docx` 第 3.1 章“网络安全能力成熟度模型”；
- 评估逻辑严格参考 `sample文档介绍.docx` 第 4 章“网络安全能力成熟度评估”；
- 后续代码实现上述两部分逻辑，不另起一套成熟度模型。

评分对象：

- `capability_focus`：关注点评估，作为最小正式评分单元；
- `capability`：能力子域评估，由关注点评估结果聚合或直接录入；
- `security_technical_service`：只作为 `platform_tool_score` 的技术输入、证据和匹配线索。

- `M-SE.SE-02` 差异较大，应优先人工确认。

## 5. 建模影响

本轮核对支持以下 M1 建模结论：

- `maturity_capability_baseline` 可以先按编码对齐主工程能力树；
- `maturity_scope_service_baseline` 保留安全技术服务输入，但不生成独立评分层级；
- `maturity_mainline_match_result` 需要支持 `name_conflict`、`code_conflict`、`ambiguous_match`、`missing_in_maturity`；
- `Reference_Mainline_Diff` Sheet 后续应从 `mainline-consistency-diff.csv` 生成，作为人工确认表；
- 正式评分前，必须先冻结一版 `model_version` 与主工程 `knowledge_base_snapshot`。

## 6. 下一步建议

1. 用户先确认 `M-SE.SE-02`、7 个主工程额外关注点，以及 V2 中缺少的 `M-PS.CT` 是否进入成熟度基准。
2. 将安全技术服务编码标准化规则写入 `config/maturity/field-mapping.sample.yaml`，例如补齐 `T-` 前缀和 `TI.IO -> T-IN.IO` 的映射。
3. 生成 `Reference_Mainline_Diff` 模板 Sheet，但仍不实现评分算法。
4. 确认差异处理口径后，再进入 `maturity_*` 迁移和模板生成 MVP。
