# 本地化结构化工作知识库系统项目计划

## 1. 项目定位

本项目要建设的是一个“结构化知识资产管理系统 + 文件解析/ETL 系统 + 本地知识门户”，而不是普通文件夹或文件预览器。

系统需要把 Excel、Draw.io、PPT、DOCX、Markdown 等资料中的内容转换为可查询、可关联、可导出、可追溯来源的知识对象，并通过本地网页或桌面程序提供统一入口。

## 2. 建设目标

- 工程代码托管在 GitHub，便于版本管理和长期维护。
- 原始文件保留在本地文件仓库中，结构化数据存入 SQLite。
- 支持文件导入、字段映射、人工编辑、批量更新、第三方 ETL 更新。
- 支持知识条目、标签、分类、来源、关系、版本、变更记录。
- 支持关键词检索、标签筛选、来源筛选、关联查询。
- 支持当前查询结果导出、按主题导出、全量导出和备份包导出。
- 通过本地 HTML 前端展示，最终可打包为本地运行程序。
- 页面和数据模型保持可扩展，便于后续加入 PPT、Draw.io、知识图谱和 AI/RAG。

## 3. 核心原则

### 3.1 先结构化，再智能化

项目第一阶段不要急于做 AI 问答。应先解决数据模型、来源追踪、导入规则、查询和导出。只有结构化数据稳定后，AI/RAG 才有价值。

### 3.2 先跑通闭环，再扩展格式

V1 应先支持 Excel、Markdown、DOCX 的最小导入闭环。PPT 和 Draw.io 可以先作为来源文件管理和浅层解析，后续再做深度解析。

### 3.3 保留原始文件和来源关系

每条知识记录都必须知道来自哪个文件、哪个 sheet、哪一页、哪一章、哪次导入任务。

### 3.4 自动导入不能静默覆盖人工编辑

批量导入和第三方 ETL 应先生成变更预览和冲突记录，由用户确认后入库。

### 3.5 开发前先完成数据定义

本项目不能直接从页面或数据库表开始。必须先从样例文件中完成数据发现、知识对象识别、字段字典、映射规则和 ETL 流程设计。

对非开发背景用户来说，推荐顺序是：

```text
样例文件盘点 → 想清楚查询/导出场景 → 识别知识对象 → 定义字段 → 建立映射 → 设计 ETL → 再开发
```

## 4. 推荐技术路线

权威技术选型记录见 `docs/technology-decisions.md`。本节只保留 V1 摘要，避免后续多处修改造成不一致。

V1 推荐：

| 层次 | 推荐方案 |
|---|---|
| 前端 | React + TypeScript |
| 桌面壳 | Tauri |
| 本地数据库 | SQLite |
| 全文检索 | SQLite FTS5 |
| ETL | Python 或 Node.js 脚本 |
| 文件存储 | 本地 data 目录 |
| 图表和视图 | ECharts、Mermaid、Draw.io viewer |
| 导出 | CSV、JSON、Excel、Markdown、HTML、ZIP |

后续增强：

| 能力 | 建议阶段 |
|---|---|
| DuckDB 分析查询 | V2/V3 |
| Draw.io 深度节点关系解析 | V2 |
| PPT 幻灯片结构化解析 | V2 |
| 关系图谱 | V2/V3 |
| 本地语义检索 / RAG | V3 |

## 5. 核心知识模型

建议采用三层结构：

```text
文件层：原始文件，如 xxx.xlsx、xxx.docx、xxx.drawio
内容层：文件内部结构，如 sheet、章节、幻灯片、图节点
知识对象层：抽取后的业务对象，如能力、流程、系统、组件、风险、指标、案例、术语
```

核心数据表：

| 表 | 作用 |
|---|---|
| `knowledge_item` | 知识条目 |
| `knowledge_source` | 来源文件 |
| `knowledge_relation` | 知识关系 |
| `tag` | 标签 |
| `item_tag` | 知识-标签关系 |
| `category` | 分类 |
| `import_job` | 导入任务 |
| `change_log` | 变更记录 |
| `export_profile` | 导出配置 |

## 6. V1 功能范围

### 必须实现

- GitHub 仓库结构；
- SQLite 数据库；
- Excel 导入；
- Markdown / DOCX 导入；
- 原始文件登记和 hash 记录；
- 知识条目列表；
- 知识详情页；
- 标签和分类；
- 关键词搜索；
- 来源追踪；
- CSV / JSON / Excel 导出；
- 全量备份包导出；
- 基础本地打包说明。

### 暂缓实现

- AI 问答；
- 完整知识图谱；
- 多人权限；
- 云同步；
- 原文件回写；
- PPT 全量深度解析；
- Draw.io 复杂图谱推理；
- 复杂冲突自动合并。

## 7. 实施阶段

本项目阶段划分以 `task_plan.md` 为唯一权威来源。本节是面向用户阅读的解释版，不另行维护独立阶段编号。

### Phase 0：需求澄清与项目规划

目标：把愿望转成明确的软件需求。

任务：

- 列出现有文件类型和样例；
- 明确知识类型清单；
- 定义知识颗粒度；
- 确定 V1 数据模型方向；
- 确定导入优先级；
- 明确哪些资料不能提交 GitHub。

输出：

- `AGENTS.md`
- `docs/project-plan.md`
- `docs/architecture.md`
- `docs/import-rules.md`
- `docs/sample-file-inventory.md`
- planning files: `task_plan.md`、`findings.md`、`progress.md`

### Phase 1：数据发现、字段定义与 ETL 设计

目标：在写代码前，先弄清楚文件里的知识如何变成字段和数据库记录。

任务：

- 盘点第一批样例文件；
- 识别每类文件中的知识对象；
- 定义第一批知识类型；
- 定义通用字段和专属字段；
- 建立 Excel、DOCX、Markdown 的映射规则；
- 定义 ETL 步骤：提取、清洗、映射、校验、暂存、审查、入库；
- 定义更新、冲突和人工审核规则。

输出：

- `docs/data-definition-guide.md`
- `docs/data-dictionary-template.md`
- `docs/sample-file-inventory.md`
- `docs/import-rules.md`
- `docs/non-developer-codex-workflow.md`

### Phase 2：工程骨架

目标：建立可维护的 GitHub 工程。

任务：

- 初始化 GitHub 仓库；
- 创建 README；
- 创建 `.gitignore`；
- 创建基础目录结构；
- 后续再初始化前端/桌面项目。

输出：

- GitHub 仓库；
- 基础目录；
- 项目说明；
- 数据安全忽略规则。

### Phase 3：数据模型设计

目标：把 Phase 1 的字段字典和映射规则转为 SQLite 数据模型。

任务：

- 设计 SQLite schema；
- 设计 staging 表；
- 设计来源文件、导入任务、变更记录表；
- 创建迁移脚本；
- 编写 `docs/data-model.md`。

输出：

- `docs/data-model.md`
- migration SQL
- 数据模型说明。

### Phase 4：导入 MVP

目标：跑通“文件进入系统 -> 结构化入库 -> 页面可查”的闭环。

任务：

- Excel 单文件导入；
- Markdown 导入；
- DOCX 基础文本/标题/表格导入；
- 记录来源文件、hash、位置；
- 生成导入任务日志；
- 支持失败提示。

输出：

- 导入页面或命令；
- `knowledge_source` 和 `knowledge_item` 入库；
- 导入日志。

### Phase 5：知识浏览、搜索和详情

目标：用户能真正使用知识库。

任务：

- 知识列表页；
- 知识详情页；
- 来源文件页；
- 标签筛选；
- 分类筛选；
- 关键词搜索；
- 最近更新；
- 待审核列表。

输出：

- 可用的本地知识门户。

### Phase 6：导出和备份

目标：避免系统形成新的数据孤岛。

任务：

- 当前查询结果导出；
- 单条知识导出；
- 分类/标签导出；
- 全量 JSON/CSV/SQLite 导出；
- 原始文件和配置打包；
- 备份 ZIP manifest。

输出：

- 导出模块；
- 备份包格式。

### Phase 7：多格式增强

目标：扩展到主要工作资料形态。

任务：

- PPT 页级解析；
- Draw.io XML 节点和连线解析；
- 文件预览图；
- 节点、幻灯片、章节来源定位；
- 解析规则可配置。

输出：

- 多格式解析能力；
- 可追溯的内容层数据。

### Phase 8：关系管理和更新审查

目标：从资料库升级为知识关系库。

任务：

- 手动建立知识关系；
- 批量导入关系；
- 关系查询；
- 导入 diff；
- 冲突检测；
- 变更审查中心；
- 版本回滚。

输出：

- 知识关系页面；
- 变更审查流程。

### Phase 9：打包交付

目标：让系统可以作为本地程序使用和备份迁移。

任务：

- 本地运行说明；
- 打包配置；
- 数据目录说明；
- 备份恢复说明；
- 用户指南。

输出：

- 本地打包产物；
- `docs/user-guide.md`。

### Phase 10：AI/RAG 增强，可选

目标：在结构化数据稳定后增加智能检索。

任务：

- 文档切片；
- 向量索引；
- 语义检索；
- 问答引用来源；
- 自动摘要；
- 自动标签；
- 自动关系推荐。

输出：

- AI 检索增强原型。

## 8. 建议的 Codex 推进方式

用户可以把项目交给 Codex 分批推进，每次只做一个明确阶段。

```text

```

```text

```

```text

```

```text
请根据 docs/sample-file-inventory.md，帮我从这些文件中提取候选知识对象和候选字段。
```


```text

```

```text

```

## 9. 用户需要准备的材料

为了让 Codex 后续能更快落地，建议准备：

- 3 到 5 个典型 Excel 文件；
- 2 到 3 个典型 DOCX 文件；
- 1 到 2 个典型 PPT 文件；
- 1 到 2 个典型 Draw.io 文件；
- 希望管理的知识类型清单；
- 希望查询和导出的几个真实例子；
- 哪些文件可以进入 GitHub，哪些只能本地保存。

## 10. 当前决策

- V1 优先做本地结构化知识库，不做 AI 起步。
- V1 优先支持 Excel、Markdown、DOCX。
- 数据库优先 SQLite。
- 本地交付优先 Tauri + React。
- 所有知识条目必须保留来源追踪。
- 批量更新必须有变更审查，不允许静默覆盖人工编辑。
