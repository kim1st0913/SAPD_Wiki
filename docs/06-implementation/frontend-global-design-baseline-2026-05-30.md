# SAPD Wiki 前端全局设计基线

日期：2026-05-30

适用范围：`frontend/capability-browser/` 当前正式前端、后续新增页面、后续重构页面、所有安全知识 / 标准 / 框架 / 能力映射 / 环境映射 / 生命周期页面。

## 1. 结论

用户不需要再写复杂提示词。后续只要表达：

```text
按全局设计基线统一这个页面。
```

或：

```text
这个页面像 Apple demo 一样整理。
```

Codex 就必须自动执行以下动作：

1. 读取 `DESIGN.md`。
2. 读取本文。
3. 读取 `docs/06-implementation/frontend-display-design-principles-2026-05-30.md`。
4. 对照 `frontend/capability-browser/apple-morandi-color-demo.html`。
5. 判断当前页面涉及哪些展示类型。
6. 使用 scoped 样式和组件级修正统一页面。
7. 验证不破坏其他页面。

这件事以后是 Codex 的责任，不是用户的提示词负担。

## 2. 单一视觉方向

SAPD Wiki 的正式前端视觉方向为：

```text
Apple shell + restrained Morandi + 专业安全架构工作台
```

含义：

- 像 macOS / iOS 工具界面一样清晰、轻、稳定。
- 使用明亮 tinted neutral 背景，不使用纯白和纯黑。
- 使用 Apple blue 作为主选中态，不到处铺蓝色。
- 使用低饱和 Morandi 语义色区分对象类型。
- 优先服务表格、矩阵、目录、图谱和关系审阅。
- 不做营销官网、卡片墙、装饰 dashboard 或泛 AI 风。

## 3. 全局设计基线

### 3.1 背景与容器

- 页面背景使用浅 tinted neutral，不使用纯白大平面。
- 应用壳、侧边栏、顶部栏、主内容区必须像一个系统，不像旧页面被塞进新壳。
- 主工作区使用低噪声边界、轻阴影、细边框。
- 不使用厚边框、重色块、强渐变、玻璃拟态。
- 不嵌套卡片。一个区域需要边界时，用 pane / section / table，而不是卡片套卡片。

### 3.2 颜色

全局颜色语义固定：

| 语义 | 颜色方向 | 用途 |
|---|---|---|
| 选中 / 当前 | Apple blue | 当前导航、当前 tab、当前选中行 |
| 当前能力 / 关注点 | muted lavender | 图谱中心、当前对象 |
| 技术视角 / 安全技术服务 | muted blue | 技术视角、服务对象 |
| 安全技术模块 | sage | 模块对象 |
| 安全技术措施 / 待补充 | clay | 措施对象或缺失提示 |
| 管理视角 / 安全职能 | sage green | 管理对象、职能、流程 |
| 标准 / 框架 | sand | 标准、条款、控制项 |
| 环境 / 弱结构 | blue-gray / slate | 信息化环境、系统、辅助结构 |
| 风险 / 异常 | muted amber / red | 仅用于异常，不用于装饰 |

禁止：

- 纯蓝、亮绿、荧光橙、紫蓝渐变。
- 每个页面临时定义一套颜色。
- 为了“好看”改变业务对象语义色。

### 3.3 字体与文字

- 使用系统字体。
- 中文业务名称优先清晰，不追求装饰。
- 页面标题紧凑，工作台标题更克制，表格正文必须可读。
- 二级目录不小于 `14px`。
- 表格正文建议 `13px` 左右，不得低到看不清。
- 表头可以比正文略强，但不能像大标题。
- 对象名称优先，编码辅助。
- 长名称省略或换行，但不得撑破布局。
- 英文标题、编码、对象名不得使用过粗字重；正常导航、表格和 chip 中英文建议控制在 `600-700`，避免 heavy / black 风格造成不清爽。
- 不使用负 letter spacing。
- 不使用 viewport 字号。

### 3.4 表格

表格是 SAPD Wiki 的核心展示方式。

统一规则：

- 表头低噪声浅底。
- 表格线细、浅、稳定。
- 行 hover 轻微提示。
- selected 行才使用明确选中态。
- 空值 `/` 使用弱样式，不做 chip。
- 对象 chip 不得比正文更重。
- 表格必须保留横向可读，不能把中文压成竖排。
- 密集表格允许横向滚动，但不能遮住关键列。
- 分组行默认策略必须稳定，不能被颜色调整改坏。
- 表格单元格必须给内部对象建立收缩边界；chip、badge、按钮不得跨出单元格、遮挡相邻列或覆盖分隔线。
- 长对象名优先在本列内省略或分行；不得依赖继续放大 / 缩小字体来掩盖列宽和溢出问题。
- 横向滚动可以承载宽表，但列内内容不得因为 `nowrap`、固定宽度或缺少 `min-width: 0` 把相邻列挤压或覆盖。
- 矩阵里的安全技术服务、模块、措施等关系对象默认只是展示对象，不自动成为能力导航入口；只有业务上明确存在目标详情页时，才允许显示为可点击控件。

禁止：

- 把表格改成卡片墙。
- 使用强色表头。
- 使用厚边框网格。
- 每个表格单独写一套字体和 chip。
- 在表格主展示区暴露调试字段或来源字段。

### 3.5 Tab 与切换

统一规则：

- tab 是导航，不是装饰卡片。
- tab 只承载稳定视图名称，不承载统计、对象数量、KPI、状态摘要或当前筛选条件。
- active 状态清晰但轻。
- 高度、间距、underline、文字大小统一。
- 不允许文字重叠。
- 不允许胶囊过大压缩内容。
- 多 Tab 场景必须先判断 Tab 类型再定布局，不允许所有 Tab 共用一种宽度策略：
  - 视角切换类 Tab，例如 `能力关系图谱 / 技术视角 / 管理视角 / 标准 / 框架映射`，数量少、语义稳定，使用内容自适应宽度或分段控件，不放统计。
  - 视角切换类分段控件必须轻：容器使用低噪声灰底，active 使用浅白胶囊和轻阴影，按钮高度和文字权重不得接近页面标题。
  - 阶段序列类 Tab，例如 LC-AP / LC-DT 阶段，数量多、结构同类，使用组内等宽；等宽值由当前组最长阶段名称 / 编码测算得出，外层横向滚动承载总宽度。
  - 长文本业务分类 Tab，如果名称差异很大，优先使用内容自适应宽度和横向滚动；不得为了整齐压缩到截断主名称。
  - 统计、数量、状态不进入 Tab；如需统计，放在 Tab 下方标题区、右侧摘要或表格摘要。
- LC-AP / LC-DT 阶段导航是特殊阶段控件，不套普通 tab 样式。
- LC-AP / LC-DT 阶段导航必须为阶段名称、编码、箭头和搜索框保留固定布局边界；窄屏可横向滚动，但单个阶段按钮不得被裁切。
- 阶段 tab 遇到空间不足时应保持组内测算等宽，由外层横向滚动承载溢出；不得把阶段按钮压缩到截断主名称，也不得让搜索框覆盖或切断最后一个阶段按钮。
- LC-AP / LC-DT 阶段 tab 不展示箭头图标；阶段按钮使用统一宽度，但统一宽度必须由当前阶段组中最长的阶段名称 / 编码测算得出，不得手写固定最大宽度；以“阶段名称 + 阶段编码”为核心内容，并保留轻微 hover / click / active 动效。
- 阶段 tab 的 active 外框、底部选中线、focus ring 必须使用同一语义色系，不允许上下两条线看起来像不同状态。
- 统计信息应放在页面标题区、内容区标题右侧或独立摘要区，不能塞进 tab / segmented control。

能力映射固定 tab 名称：

- `能力关系图谱`
- `技术视角`
- `管理视角`
- `标准 / 框架映射`

禁止：

- 使用“技术路径”“管理路径”等未经确认的替代名。
- 用全局 tab CSS 误伤生命周期阶段导航。

### 3.6 目录与树

统一规则：

- 一级导航负责全局定位。
- 二级导航负责模块入口，必须清晰可读。
- 页面内树目录负责对象选择。
- 一级导航的彩色图标底必须和前景图案形成清晰对比；图案不可被渐变底、选中态内层底或同色系低对比色吞掉。
- 当前选中态要明显，但不能大面积高饱和。
- 展开 / 收起必须保留原交互。
- 默认展开 / 收起策略不能因为视觉修改改变。
- 长名称必须省略或合理换行。

禁止：

- 二级目录变成脚注大小。
- 目录选中态和 hover 态混淆。
- 目录项高度被图标、chip 或临时 padding 撑坏。

### 3.7 Chip、Badge、状态

统一规则：

- chip 表示业务对象，不表示空值。
- badge 表示状态，不表示对象。
- 数量角标只承载数量，不抢主内容。
- chip 颜色按对象类型，不按页面喜好。
- 同一对象在不同页面颜色一致。
- 安全技术服务、模块、措施、管理对象、标准 / 框架在能力映射、环境映射、LC-AP / LC-DT、安全知识和安全标准页面中必须使用同一语义色。
- 关系对象 chip 必须包含可收缩文本容器，主体名称可省略，类型前缀和对象类型颜色保持稳定。
- chip 必须受所在单元格、面板或列表边界约束，不能为了显示完整文本跨列、悬浮到相邻区域或改变表格列宽。
- chip 只有在具有明确业务跳转目标时才能表现为链接或按钮；普通关系对象 chip 不承担页面导航，避免点击安全技术服务 / 模块误跳到能力图谱。

禁止：

- `/`、`暂无`、`待补充` 被渲染成对象 chip。
- 一个单元格里堆满 chip 导致行高失控。
- 状态 badge 使用过强颜色。

### 3.8 图谱

统一规则：

- 图谱用于总体关系展示。
- 表格用于分 tab 的结构化审阅。
- 图谱和表格必须使用同一数据投影，只是展示形式不同。
- 当前能力 / 关注点作为中心锚点时，只显示必要名称和编码。
- 没有真实数据的节点不显示。
- 线条低噪声，节点层级清楚。
- 颜色按语义角色，不按临时层级随意变化。

禁止：

- 伪造节点。
- 用空节点撑画面。
- 图谱里显示 raw / debug / 来源字段。
- 因视觉修改改变数据来源或 ViewModel 业务逻辑。

### 3.9 空状态与来源证据

统一规则：

- 空状态要说明为什么为空。
- 无直接映射时写清楚“当前数据包暂未提供直接映射”。
- 业务级 `参考来源` 可以作为表格单元格内的辅助信息展示，但必须使用统一结构：上方标签 `参考来源`，下方低噪声浅色圆角引用框。
- `参考来源` 引用框用于承载标准条款、文件级业务引用、数据库表或字段级业务引用等用户可读来源，不使用 chip、不使用强色块、不裸露为普通长文本。
- 同一单元格内有多条业务参考时合并到同一个引用框内，用中文分隔符串联，避免一格内堆叠多个胶囊。
- 业务级 `参考来源` 和原始来源证据必须区分：前者是业务可读引用，后者是导入、行列、原始文件等追溯证据。
- 来源证据默认折叠。
- 来源证据不挤压主表格、主图谱。
- 错误状态不展示技术堆栈。

禁止：

- 用假数据填空。
- 用大面积空卡占据主界面。
- 把 `sheet`、`row`、`source_file`、`raw_value` 等原始来源字段放入主表格。
- 把业务 `参考来源` 显示成裸文本、重边框胶囊、导航按钮或状态 badge。

## 4. 页面一致性要求

后续新页面和已完成页面都必须按本文统一。

### 4.1 新开发页面

新页面必须先套全局基线，再写业务细节：

1. 应用壳一致。
2. 页面标题一致。
3. tab 一致。
4. 表格一致。
5. 目录一致。
6. chip / badge 一致。
7. 空状态一致。
8. 字段边界一致。

### 4.2 已完成页面

已完成页面如果与基线不一致，应作为视觉债务处理。

优先级：

1. 表格可读性。
2. tab 不重叠。
3. 目录字号和层级。
4. chip / 空值口径。
5. 图谱语义色和布局稳定。
6. 详情 / 来源证据收敛。

### 4.3 局部修改

即使用户只说“这个地方像 demo 一样改”，Codex 也必须检查：

- 是否误伤同类 tab。
- 是否误伤同类表格。
- 是否误伤 LC-AP / LC-DT 特殊控件。
- 是否误伤环境映射 5 列 / 3 列列宽。
- 是否造成字段泄露。
- 是否改变数据投影。

## 5. 用户最简需求表达

用户以后可以只说：

```text
按全局设计基线统一这个页面。
```

或：

```text
这个页面参考 Apple demo 调整。
```

或：

```text
这里看起来不统一，按基线修。
```

或：

```text
表格 / tab / 目录 / 图谱 按全局基线整理。
```

Codex 必须自己补齐：

- 要读哪些文件。
- 涉及哪些展示类型。
- 哪些样式需要 scoped。
- 哪些页面需要回归。
- 哪些字段不能显示。
- 哪些验证必须执行。

## 6. Codex 后续执行协议

每次涉及前端视觉、展示或页面改动时，Codex 必须在执行前确认：

```text
本轮按全局设计基线执行。
涉及展示类型：[表格 / tab / 目录 / 图谱 / ...]
不会修改数据链路、ETL、数据库、导出 JSON。
```

实现时：

- 优先复用现有 token 和 class。
- 优先 scoped 到具体组件或页面。
- 不使用宽泛选择器批量覆盖。
- 不改变业务数据投影。
- 不引入新依赖。

完成时：

- 说明修改了哪些展示类型。
- 说明是否影响其他页面。
- 说明验证命令。
- 说明字段边界是否检查。

## 7. 验收标准

全局设计基线执行合格，必须满足：

1. 看起来属于同一个产品。
2. 与 Apple demo 的颜色、表格、tab、chip、目录方向一致。
3. 表格不竖排、不挤压、不重边框。
4. tab 不重叠、不变形。
5. tab 不显示统计、KPI 或对象数量。
6. 二级目录清晰可读。
7. 表格内 chip 不跨列、不遮挡、不把相邻列挤压变形。
8. LC-AP / LC-DT 阶段导航不裁切阶段按钮，搜索框位置稳定。
9. 安全技术服务、模块、措施等语义对象在不同页面颜色一致。
10. 图谱和表格数据口径一致。
11. 空值、缺失、待确认状态一致。
12. 主展示区无非业务字段泄露。
13. 1440px 可读。
14. 1920px 舒展。
15. 不破坏已有页面。
16. `git diff --check` 通过。
17. 前端页面修改后执行对应 smoke 或浏览器验证。

## 8. 与其他设计文档的关系

- `DESIGN.md` 是最高层设计入口。
- 本文是全局设计基线。
- `frontend-display-design-principles-2026-05-30.md` 是展示类型细则。
- `apple-color-direction-handoff-2026-05-29.md` 是颜色方向交接。
- `apple-morandi-color-demo.html` 是可视化参考。

后续如果这些文档冲突，执行顺序为：

1. 用户最新明确要求。
2. `DESIGN.md`
3. 本文。
4. 展示类型细则。
5. 颜色交接文档。
6. 具体 demo。
