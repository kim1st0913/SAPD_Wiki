# 执行线收敛工作流

本文档用于解决 SAPD Wiki 项目中“会话过多、执行线过多、上下文变重、子 Agent fan-in 不稳定”导致的推进成本问题。它不是新增功能计划，而是后续所有复杂任务的默认执行方式。

## 当前问题定义

前期并行会话不是管理失误，而是被以下工程约束逼出来的临时做法：

- 子 Agent 调用、等待或 fan-in 不稳定，导致主控不能稳定依赖并行结果。
- 单会话执行时间变长后，恢复、读取、验证和输出都会变慢。
- 多会话并行短期提高了推进速度，但长期带来 dirty diff 混杂、任务线漂移、治理文档分叉和验收口径不一致。

因此后续优先目标不是“继续加速并行”，而是先恢复可控性：

```text
单一主控
+
单一写入主线
+
短闭环验证
+
明确 checkpoint
```

## P0 收敛原则

### 1. 一个主控负责最终判断

任何会话、子 Agent 或外部审查结果都只能提供事实和建议。是否采纳、是否写入 `open-issues.md`、是否更新 `CURRENT_STATE.md`、是否进入 checkpoint，统一由主控决定。

主控必须维护四类状态：

- 当前唯一写入任务；
- 当前 dirty diff 范围；
- 当前验证门槛；
- 当前暂停或后置的任务线。

### 2. 一个时间点只允许一条写入主线

除非用户明确批准并且写入范围完全不重叠，否则同一时间只允许一个任务修改文件。

禁止同时写入这些高风险组合：

- `app.js` + `viewModels.js` + `styles.css`；
- `dataClient` + ViewModel + API projection；
- ETL / export + 前端数据包消费；
- `open-issues.md` + 归档问题 + 当前状态入口；
- Delivery Bundle 脚本 + 前端展示逻辑。

### 3. Dirty worktree 优先于新功能

如果 `git status --short --branch` 显示大量未提交改动，后续任务默认先做 dirty diff 验收，不直接启动新功能。

推荐顺序：

1. `git diff --stat` 看主题分布。
2. 按文件组局部读取 diff。
3. 跑该组对应治理脚本。
4. 决定是 checkpoint、继续修正，还是请用户确认是否丢弃某条线。

### 4. 长任务拆成 30-60 分钟闭环

每个闭环必须能回答：

- 本轮只解决什么问题；
- 会读或改哪些文件；
- 成功验收命令是什么；
- 失败后如何回退；
- 是否需要用户业务判断。

如果不能回答，先做只读 Gap Check，不进入实现。

## 当前执行线重排

| 优先级 | 执行线 | 当前处理 |
|---|---|---|
| P0 | 工作区 dirty diff 验收与 checkpoint | 先验收当前未提交前端、治理文档和 Delivery 脚本改动，再决定是否提交 |
| P0 | 执行治理收敛 | 固化本工作流，并在后续会话默认执行 |
| P1 | 安全能力映射数据加载稳定性治理 | `OI-132 / EL-024`；继续改安全能力页前，先建立 workspace-view / projection / fallback / tab rows 的诊断和回归门槛 |
| P1 | 前端治理基线失败项 | `audit_frontend_governance.mjs` 失败时不继续叠 CSS / app.js 补丁 |
| P1 | 权威字典引用一致性 | `audit_dictionary_reference_consistency.mjs` 失败项进入数据治理闭环 |
| P1 | `OI-128` 收藏最小入口 | 在 ID / user DB 边界稳定后再做，优先收藏，备注后置 |
| P2 | Windows ZIP UAT | 用户已明确后置，不作为当前默认任务 |
| P2 | maturity / Phase 7 / Tauri | 默认暂停，除非用户重新指定 |

当前执行线的完整台账见 `docs/07-governance/current-execution-lines.md`。暂停任务前必须先登记到台账，确保后续可以恢复。

如果用户已经按模块开了多个线程，不要求立即关闭。先把每个线程映射到台账中的 `EL-xxx`：

```text
线程 / 模块名：
对应 EL：
当前权限：只读 / 可写
正在做什么：
最后证据：
需要 fan-in 的结论：
是否继续运行：
```

未完成映射的线程默认视为辅助只读线程，不能继续写入主状态文件或高风险公共代码。

## 新会话启动协议

新会话接手时默认只做以下轻量读取：

```bash
git status --short --branch
git diff --stat
sed -n '1,220p' CURRENT_STATE.md
tail -n 120 progress.md
```

必要时再读取：

- `docs/00-overview/master-context-restore.md`
- `docs/07-governance/governance-index.md`
- 当前任务直接相关的治理文档或目标文件局部。

默认不读取：

- `docs/05-archive/` 完整历史；
- `data/exports/`；
- `frontend/capability-browser/public/data/*.json`；
- 数据库和备份；
- 全量 `git diff`。

## 长会话轮换协议

开新会话不是问题，失控的点在于“新会话变成新执行线”。后续允许主动轮换会话，但必须保留同一个 `EL-xxx` 和同一个写入范围。

### 用户明确卡顿交接协议

只有当用户明确说“当前会话卡顿，需要交接”“这个会话太慢，交接到新会话”“请开新线程接手”或等价表达时，Codex 才允许自动进入会话交接流程。

触发后，当前会话必须按以下顺序执行：

1. 立即停止当前会话的代码修改和长任务执行；若已有命令仍在运行，先给出状态，不继续扩大写入范围。
2. 整理交接包，必须包含：仓库状态、已完成事项、下一步、先读文件、禁止优先读取的大文件、未提交改动和验证要求。
3. 创建同名递增的新线程，例如 `V3` 后创建 `V4`；如果当前线程名没有版本号，使用同名加 `V2`。
4. 将交接包写入新线程初始提示，并声明新线程继续同一个 `EL-xxx` 或当前主线，不得把交接变成新执行线。
5. 当前会话最终回复后发出归档指令，不再继续执行代码、验证或新任务。
6. 如果用户没有明确说“卡顿交接”或等价表达，Codex 不得自动创建新线程；只能建议用户选择是否交接，或继续在当前会话做短闭环。

交接包推荐模板：

```text
当前线程：
建议新线程名：
当前 EL / 主线：
仓库状态：
未提交改动：
已完成事项：
下一步只做什么：
开工先读：
不要优先读取：
禁止范围：
验证要求：
前端固定入口：
真实库 / 用户库写入状态：
```

### 建议轮换的条件

满足任一条件时，主控可以建议用户结束当前闭环并换新会话，但在用户明确确认“卡顿交接”前，不得自动创建新线程：

- 单会话连续工作超过 60-90 分钟，工具响应、恢复或阅读明显变慢。
- 同一会话已经处理 3 个以上文件组，开始难以说明当前唯一写入目标。
- 上下文里同时混入前端、数据、Delivery、治理文档等多个主题。
- `progress.md` 接近或达到 120 行，需要先归档瘦身。
- 出现多次等待超时、工具输出过长、或用户需要临时切换任务。

### 旧会话退出前必须留下的换班包

旧会话在换班前不需要写长篇总结，但必须更新或输出以下 8 项：

```text
当前 EL：
当前状态：当前主线 / 待验收 / 暂停 / 后置 / 待确认
已改文件：
未改禁止范围：
已跑验证：
未完成原因：
下一步只做什么：
仍在运行的 thread id：
```

如果已经改文件，优先跑：

```bash
git status --short --branch
git diff --stat
git diff --check
```

需要进入 checkpoint 时，先让用户确认，不在旧会话卡顿状态下继续扩大改动。

### 新会话接手规则

新会话的第一句话必须声明接手哪个 `EL-xxx`。启动后只读取：

- `CURRENT_STATE.md`
- `docs/07-governance/current-execution-lines.md`
- `progress.md` 最近状态
- 当前 EL 直接相关文件局部

新会话不得因为看到旧线程标题就自动恢复旧模块；必须按执行线台账判断：

- 如果 EL-001 还没完成，继续 dirty diff 验收。
- 如果旧线程是 `归档参考`，只读结论，不恢复它。
- 如果旧线程是 active / inProgress，只等 fan-in，不抢写。
- 如果用户要求继续某模块，也要先映射到对应 `EL-xxx`。

### 旧会话归档时机

旧会话只有在新会话已成功接手，并且换班包已经落到 `CURRENT_STATE.md`、`progress.md` 或 `current-execution-lines.md` 后，才建议归档。

归档优先级：

1. 重复线程和历史主控线程。
2. 已完成且已写入正式文档的只读预研线程。
3. 已完成的问题排查线程。
4. 已完成的单页面交接线程。

不归档：

- active / inProgress 线程；
- 仍在写文件的线程；
- 还没有 fan-in 结论的线程；
- 用户明确要求保留观察的线程。

## 子 Agent 使用降级规则

在子 Agent 稳定性没有重新证明前，子 Agent 默认降级为“只读审查线程”。

允许：

- 页面 Gap Check；
- 数据包或源表事实核对；
- 文档草案；
- UAT checklist 草案；
- 只读风险复盘。

不允许默认交给子 Agent 写入：

- 前端公共文件；
- ETL / export；
- `open-issues.md`；
- `CURRENT_STATE.md`、`task_plan.md`、`findings.md`、`progress.md`；
- Delivery Bundle 构建脚本。

如果必须让子 Agent 写入，启动前必须写清：

```text
Agent 角色：
任务目标：
唯一写入范围：
禁止范围：
验收命令：
fan-in 格式：
停止条件：
```

## 多会话并行规则

多会话可以存在，但必须分成以下两类：

| 类型 | 是否可写 | 用途 |
|---|---:|---|
| 主控会话 | 可写 | 唯一采纳和合并入口 |
| 辅助会话 | 默认只读 | 审查、核对、草案、定位风险 |

辅助会话如果发现问题，只输出：

- 事实证据；
- 涉及文件；
- 建议优先级；
- 建议验证命令；
- 是否需要用户业务判断。

辅助会话不得直接改主状态文件，也不得和主控同时改同一组代码文件。

多会话与模块线程的对应关系维护在 `docs/07-governance/current-execution-lines.md` 的“模块线程映射”表。主控不按线程标题判断优先级，只按对应 `EL-xxx`、状态和写入范围判断。

页面模块线程需要额外声明页面类型，例如 `capability-mapping-workbench`、`document-page`、`standard-framework-page` 或 `knowledge-directory`。安全指南、标准 / 框架、安全能力映射、安全知识目录、信息化环境和生命周期页面都必须作为独立页面模块线程追踪，不能全部折叠成“前端线程”。

## 当前任务选择规则

当用户只说“继续执行”时，默认按以下排序选择任务：

1. 若 dirty diff 未验收，先验收 dirty diff。
2. 若治理脚本失败，先解释失败项并选择一个 P0 / P1 修复。
3. 若 `progress.md` 超过 120 行，先归档瘦身。
4. 若前端最近改动未验证，先跑轻量 smoke 和对应审计。
5. 若工作区干净且治理通过，再启动下一个功能任务。

## 交付反馈要求

完成任一闭环后，最终反馈必须额外说明：

- 是否新增执行线；
- 是否关闭或暂停了执行线；
- 当前唯一建议下一步；
- 是否需要 checkpoint commit；
- 哪些任务明确后置。

这样用户不需要在多个会话之间记忆项目状态，后续 Codex 也能从轻量入口恢复。
