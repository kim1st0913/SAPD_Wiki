## 2. 总体结论

新业务设计文档与当前 SAPD Wiki 工程 maturity 方向总体一致，可以作为下一阶段成熟度模块的数据契约、页面契约和后端设计输入。

需要固化的核心结论：

| 主题 | 审阅结论 |
|---|---|
| 数据权威源 | 能力、关注点、安全技术服务、作用域及关系必须以工程内已治理字典为准 |
| 原始材料定位 | Word、旧 XLSX、V1.2 Markdown 只提供方法论、等级描述、rubric 文案和历史模板参考 |
| 页面归属 | 说明类内容放入 `安全指南 > 成熟度模型使用指南`；评估工作流放入 `工作台 > 成熟度评估` |
| 评分对象 | 直接评分对象为 `capability` 和 `capability_focus` |
| 安全技术服务 | 不作为独立评分对象，只作为 `platform_tool_score` 的技术输入、证据线索和建议出口 |
| 运行数据边界 | 客户输入、证据、匹配、评分、差距、建议和报告快照进入 maturity 专用对象，不写入 `knowledge_items` |
| 前后端边界 | 前端只展示 maturity 服务层输出，不实现 ETL、匹配、评分或主数据归一 |

## 4. 原始材料审阅结论

### 4.1 Word 方法论文档

`网络安全成熟度模型介绍V 0.6.docx` 已成功转为 Markdown 做只读抽取。其结构与当前业务设计文档一致，核心章节包括：

- 网络安全能力成熟度模型概述；
- 设计依据；
- 网络安全能力成熟度模型；
- 网络安全能力成熟度评估；
- 网络安全能力成熟度模型应用。

其中最应被工程实现采信的是：

| Word 章节 | 对工程的作用 |
|---|---|
| 3.1 模型架构 | 定义能力等级、能力要素、能力域和子域 |
| 3.1.1 能力等级定义 | 支撑 L1-L5 等级说明 |
| 3.1.2 能力要素解析 | 支撑四要素评分 |
| 3.1.3 能力域及能力子域 | 只作方法论说明，不覆盖工程字典 |

| 5.2 主要应用示例 | 支撑报告章节和应用场景说明 |

采信限制：

- Word 中的能力域、子域、名称、数量只能作为文字参考；
- 工程中的能力分类、L1、L2、关注点、服务和作用域必须以当前字典为准。

### 4.2 V1.2 Markdown 评估表

`能力成熟度评估表_V1.2.md` 覆盖了 L2 安全能力成熟度定义和 L2 安全能力评估明细。它的主要价值是提供更现实的 L1-L5 rubric 文案，尤其是对 L5 做了现实性校准。

审阅到的关键口径：

- L3 是多数组织的目标等级；
- L4 是领先企业目标；
- L5 多数情况下是理论级、极少组织达到或战略愿景；
- 每个 L2 能力给出 `能力描述` 和 L1-L5 描述；
- 当前业务设计文档识别到 V1.2 只覆盖 31 个 L2 能力，而工程稳定字典有 32 个 L2 能力。

采信建议：

| 内容 | 处理 |
|---|---|
| 通用 L1-L5 定义 | 进入 `maturity_level` 或 `maturity_level_definition` |
| L2 能力 rubric | 进入 `maturity_rubric` 或 `maturity_capability_baseline` |
| L5 现实性说明 | 进入报告解释和评分警示 |
| L2 能力列表 | 不作为权威能力清单，只作 rubric 覆盖清单 |
| 缺失的 `M-PS.CT` rubric | 作为 maturity rubric 缺口处理，不反向修改主工程能力字典 |

### 4.3 旧 XLSX 评估工具

`网络安全成熟度评估工具-v1.1-20260513.xlsx` 是旧版评估工具，本轮只读检查结果：

| Sheet | 行列 | 合并单元格 | 审阅判断 |
|---|---:|---:|---|
| `成熟度级别` | 3 行 × 11 列 | 9 个 | 可参考 L1-L5 通用等级说明 |
| `成熟度分级描述` | 176 行 × 13 列 | 280 个 | 可参考关注点、作用域、技术服务和等级描述混排结构 |

重要判断：

- 该 XLSX 合并单元格很多，不能用 CSV 化或简单向下填充方式直接当权威输入；
- 它更适合作为历史模板结构和文字来源；
- 安全能力、关注点、服务、作用域和关系不以该 XLSX 为准；
- 正式模板应采用显式字段，不应复刻旧 XLSX 的混排和合并单元格结构。

## 7. 需要谨慎处理的差异

| 差异 | 风险 | 建议 |
|---|---|---|
| 新业务设计中有 CSV 快照数量 | 容易被误当成静态硬编码 | 正式实现从工程字典和知识库快照读取，不硬编码数量 |
| V1.2 rubric 覆盖 31 个 L2，工程字典 32 个 L2 | 评分模板可能缺一项 rubric | 作为 maturity 模型缺口处理，不修改工程字典 |
| 服务描述字段为空 | 报告无法生成服务解释 | 报告只展示服务编码、名称、作用域、模块 / 产品摘要；服务说明后续补充 |
| 25 个关注点无服务映射 | 平台工具维度不能完全由服务支撑 | 允许无服务映射，平台工具评分以证据和人工判断为准 |
| 当前工作台 mock 维度是治理 / 技术 / 运营 / 证据完整性 | 容易与四要素评分混淆 | 正式评分页必须使用四要素；治理 / 技术 / 运营只可作为报告展示聚合 |
| L0 容易被当作正式等级 | 成熟度解释失真 | L0 作为工具状态，不作为正式 L1-L5 成熟度等级 |
| 新增作用域子类暂不纳入 | 后续可能有迁移成本 | 当前按稳定字典实现，作用域变化由字典层统一处理 |

## 8. 建议下一步

建议按以下顺序推进：

1. 更新 `docs/08-maturity/scoring-rules.md`，补充证据等级、证据折减、关键项短板约束、L0/N/A 语义和 L5 现实性说明。
2. 更新 `docs/08-maturity/maturity-data-model.md`，吸收 `maturity_template`、`maturity_rubric`、`assessment_evidence`、`assessment_score_entry`。

4. 新增 API 契约草案，先定义 `/api/v1/maturity/projects`、`/score`、`/matches`、`/gaps`、`/recommendations`、`/report-snapshot`。
5. 后续再进入代码实现，不直接从旧 XLSX 或外部 Markdown 写入主工程字典。
