# 成熟度分析模块需求规划

本文档定义 SAPD Wiki 下独立 `maturity` 模块的需求边界。输入依据包括当前工程规划、数据模型、前后端边界文档，以及外部 PRD `security_maturity_analysis_prd_v0_2.md`。

## 1. 模块定位

成熟度分析模块不是独立项目，也不是把评估结果塞进知识库主表的新对象类型。它应作为 SAPD Wiki 主工程下的独立业务模块，读取现有安全能力知识库，生成客户安全能力成熟度评估模板，导入员工填写的现状材料，完成匹配、审查、评分和报告输出。

核心定位：

```text
SAPD Wiki 知识库主模块：维护安全能力、关系、来源和前端投影
maturity 模块：基于安全能力知识库执行客户评估，不污染知识主数据
```

## 2. 设计边界

| 边界 | 规则 |
|---|---|
| 工程归属 | 属于 SAPD Wiki 主工程，后续代码落在独立 `maturity` 模块 |
| 数据边界 | 评估运行数据使用 `maturity_*` 专用表，不写入 `knowledge_items` |
| 知识库依赖 | 只读取现有 `capability_category`、`capability_domain`、`capability`、`capability_focus` 等知识对象 |
| 来源追踪 | 复用 `source_files`、`import_jobs`、`source_references` 的思想，记录模板文件、Sheet、行号、字段和规则版本 |
| 当前实施范围 | 本轮只做 M0 文档和 YAML 配置，不实现复杂评分代码、图表代码和 UI |
| 前端边界 | V1 先 CLI + Excel + JSON/Markdown/HTML 报告，V1.1 再接入页面 |
| 客户数据 | 客户输入、评估结果和报告默认保存在本地 `data/maturity/`，不提交 GitHub |

业务逻辑来源固定为：

- 模型设计严格参考 `sample文档介绍.docx` 第 3.1 章“网络安全能力成熟度模型”，包括模型架构、能力等级定义、能力要素解析、能力域及能力子域；
- 评估逻辑严格参考 `sample文档介绍.docx` 第 4 章“网络安全能力成熟度评估”，包括关注点评估、能力子域评估、能力域评估、总体能力评估、计分方式和评估流程；
- 后续后端代码、模板字段和报告结构都应实现这两部分业务逻辑，不另起一套模型。

## 3. V1 目标

| 编号 | 目标 | 验收口径 |
|---|---|---|
| G1 | 生成标准 Excel 评估模板 | 模板包含评估信息、现状输入、证据清单、人工调整、能力参考和填写说明 |
| G2 | 导入员工填写模板 | 能解析 50-200 行客户现状输入，并输出校验结果 |
| G3 | 匹配安全能力关注点 | 填写能力编码时精确匹配；未填写编码时输出候选能力、置信度和解释 |
| G4 | 保留人工审查 | 低置信度匹配不得直接进入正式评分，先导出审查表 |
| G5 | 生成 L0-L5 成熟度评分 | 按 `capability_focus` 评分，并向 L2、L1、分类和整体聚合 |
| G6 | 输出离线报告数据 | 输出 JSON、Markdown、HTML 报告和图表数据结构 |
| G7 | 保留完整追溯链 | 结果能追溯到模板版本、规则版本、知识库快照、输入行和匹配依据 |

## 4. V1 非目标

- 不开发复杂前端页面。
- 不开发图表渲染代码。
- 不生成 PPTX 报告。
- 不引入在线 API 或云端语义模型。
- 不把客户现状、评分结果、报告写入 `knowledge_items`。
- 不改动现有 Excel ETL、能力浏览前端和主线导入链路。

## 5. 用户与流程

| 用户 | 主要动作 |
|---|---|
| 咨询顾问 / 评估人员 | 生成模板、填写客户现状、导入、审查匹配、导出报告 |
| 售前 / 架构师 | 查看能力短板、优先级、目标等级差距和改进建议 |
| 项目经理 | 跟踪多次评估结果和改进前后变化 |
| 知识库维护者 | 维护安全能力、关键词、评分规则和模板版本 |

V1 流程：

```text
生成评估模板
→ 员工填写客户现状与证据
→ 导入模板并校验
→ 自动匹配能力关注点
→ 导出低置信度匹配审查表
→ 导入人工审查结果
→ 规则评分
→ 汇总到 L2 / L1 / 分类 / 整体
→ 导出 JSON / Markdown / HTML 报告
```

## 6. 初始样例输入

用户已明确 maturity raw sample 包括一个 Word、一个 PPTX 和一个 XLSX。建议后续本地放入：

```text
data/raw-samples/maturity/
├─ <客户现状或访谈纪要>.docx
├─ <现有评估汇报或客户材料>.pptx
└─ <成熟度评估输入模板或样例>.xlsx
```

三类样例在 M1/M2 的用途：

| 样例 | 用途 |
|---|---|
| Word / DOCX | 提炼客户现状描述、证据摘要和报告正文风格，不作为 V1 自动评分必需输入 |
| PPTX | 参考评估汇报结构、图表口径和客户沟通表达，不在 V1 自动生成 PPT |
| XLSX | 作为 V1 模板生成、导入校验、匹配审查和评分闭环的主输入 |

这些样例属于本地敏感资料，默认不提交 GitHub。

## 7. 后端与前端约束

后端负责事实和规则：模板生成、文件登记、模板解析、字段校验、匹配候选、评分、汇总、报告数据导出。

前端只消费后端或静态导出的结果：评估列表、匹配审查、结果总览、能力明细和报告导出。前端不得从原始模板字段自行推断能力关系或评分结果。

## 8. 待进入 M1 前确认

| 问题 | 建议默认值 |
|---|---|
| 成熟度等级是否采用 L0-L5 | 是 |
| 主模型是否采用“安全能力维 × 落地要素维 × 成熟度等级维” | 是 |
| V1 是否先 CLI + HTML 报告，不做完整前端 | 是 |
| 员工是否必须选择能力编码 | 不强制，但强烈建议 |
| 低置信度匹配是否必须人工审查 | 是 |
| V1 是否输出 PPTX | 否，V2 再做 |
