# 成熟度分析模块评分规则设计

本文档定义 maturity 模块 V1 的规则评分口径。当前只做规则设计和 YAML 配置占位，不实现评分代码。

业务逻辑来源：

- 模型设计严格参考 `sample文档介绍.docx` 第 3.1 章“网络安全能力成熟度模型”；
- 评估逻辑严格参考 `sample文档介绍.docx` 第 4 章“网络安全能力成熟度评估”；
- 后续评分代码不得重新发明模型，只能把第 3.1 章和第 4 章的业务逻辑结构化实现。

## 1. 评分模型

V1 采用三维模型：

```text
安全能力维 × 落地要素维 × 成熟度等级维
```

| 维度 | 说明 |
|---|---|
| 安全能力维 | 读取 SAPD Wiki 现有能力树，正式评分对象为 `capability` 和 `capability_focus` |
| 落地要素维 | 判断能力是否具备组织与角色、制度与流程、平台与工具、数据与信息四类支撑 |
| 成熟度等级维 | 使用 L0-L5 表示从无证据到持续优化的成熟度，其中 L1-L5 来自模型基准，L0 为系统内部缺失态 |

上下文维度，如业务范围、场景、信息化环境、生命周期和作用域，用于筛选、解释和报告展示。作用域下的安全技术服务不是独立评分对象，而是 `platform_tool_score` 的技术输入、证据和匹配线索。

## 2. 成熟度等级

| 等级 | 名称 | 默认分 | 判断含义 |
|---|---|---:|---|
| L0 | 未覆盖 / 无有效证据 | 0 | 没有有效输入、证据或匹配 |
| L1 | 临时执行 | 20 | 有零散实践，依赖个人经验 |
| L2 | 计划跟踪 | 40 | 有职责、计划、局部流程或局部工具，能重复执行但覆盖有限 |
| L3 | 充分定义 | 60 | 组织、流程、技术和运营较完整，能在主要范围稳定落地 |
| L4 | 量化控制 | 80 | 在 L3 基础上，有指标、审计、监控、报表或效果度量 |
| L5 | 持续优化 | 95 | 在 L4 基础上，能基于度量、事件、审计或风险变化持续改进 |

## 3. 固定评分要素与默认权重

| 要素 | 字段 | 默认权重 | 作用 |
|---|---|---:|---|
| 组织与角色 | `organization_role_score` | 0.25 | 判断职责、部门、岗位、责任边界和责任落实 |
| 制度与流程 | `process_system_score` | 0.25 | 判断制度、流程、SOP、审批、例外管理 |
| 平台与工具 | `platform_tool_score` | 0.25 | 判断工具、平台、产品、技术措施和自动化能力 |
| 数据与信息 | `data_information_score` | 0.25 | 判断安全数据记录、采集、关联、分析和决策支持 |

四个评分要素为当前成熟度模型固定口径。后续如需要调整权重或增加要素，必须创建新的 `maturity_model_version` 和 `rule_set_version`，不能在同一版本中混用不同口径。

## 4. 等级门槛

| 等级 | 最低条件 |
|---|---|
| L0 | 无有效输入、无证据、无匹配 |
| L1 | 有零散实践或口头认知，但缺少稳定职责、流程、工具和信息记录 |
| L2 | 四个要素中至少一个要素达到可重复执行状态 |
| L3 | 组织与角色、制度与流程、平台与工具三个核心要素基本成形，数据与信息有基本记录 |
| L4 | 四个要素均有稳定支撑，并能通过数据、指标、监控、报表或审计进行量化控制 |
| L5 | 在 L4 基础上，能基于数据、事件、审计、风险变化或业务变化持续优化 |

## 5. 匹配规则

自动匹配用于把模型基准或客户输入行映射到主工程已治理对象。评分对象匹配目标包括 `capability` 和 `capability_focus`；安全技术服务只作为平台与工具维度的技术输入进行辅助匹配。

| 优先级 | 方法 | 分数建议 | 处理 |
|---|---|---:|---|
| P0 | 能力编码精确匹配 | 100 | 自动接受 |
| P1 | 标题 / 别名精确匹配 | 90 | 自动接受 |
| P2 | 关系扩展匹配 | 70-85 | 高分可接受，低分需审查 |
| P3 | 关键词规则匹配 | 50-75 | 多数需要审查 |
| P4 | 本地模糊文本匹配 | 40-70 | 只作候选 |

候选状态：

| 分数 | 状态 | 说明 |
|---:|---|---|
| 85-100 | `auto_accepted` | 可自动进入评分，但保留审查记录 |
| 60-84 | `needs_review` | 进入人工审查 |
| 40-59 | `weak_candidate` | 仅参考，不直接评分 |
| 0-39 | `unmatched` | 未匹配 |

## 6. 评分流程

```text
读取已确认匹配
→ 识别评分对象类型 capability / capability_focus
→ 汇总组织、流程、技术服务、数据证据
→ 判断各落地要素是否有效
→ 应用等级门槛
→ 计算成熟度分数和置信度
→ 生成 scoring_detail_json
→ 按关注点 → 能力子域 / capability → 能力域 / domain → 总体能力 / overall 聚合
```

V1 不使用黑盒模型直接评分。后续可以增加本地语义匹配，但必须保留规则解释和人工覆盖。

## 7. 聚合规则

V1 简化聚合：

```text
聚合成熟度分数 = 子项成熟度分数平均值
```

后续保留权重扩展：

```text
聚合成熟度分数 = Σ(子项分数 × 权重 × 置信度修正) / Σ(权重 × 置信度修正)
```

等级由聚合分数回填：

| 分数 | 等级 |
|---:|---|
| 0-9 | L0 |
| 10-29 | L1 |
| 30-49 | L2 |
| 50-69 | L3 |
| 70-89 | L4 |
| 90-100 | L5 |

## 8. 人工覆盖

人工覆盖必须记录：

- 原始自动等级；
- 覆盖后等级；
- 覆盖原因；
- 审查人；
- 审查时间；
- 影响的输入行或证据。

覆盖后的结果仍写入 `maturity_score_result`，但 `reviewer_override` 必须为 true。

## 9. 主工程一致性核对规则

在正式评分前，maturity 模型基准必须先与主工程已治理数据做一致性核对。

核对优先级：

| 优先级 | 对象 | 核对方式 |
|---|---|---|
| P0 | 能力关注点 | 使用 `capability_focus_code` 精确匹配 |
| P1 | L2 安全能力 | 使用名称、父级 L1 和已有关系匹配 |
| P2 | L1 能力域 | 使用名称和能力分类匹配 |
| P3 | 安全技术服务输入 | 使用 `scope_type + service_name + capability_focus_code` 组合匹配，作为平台与工具评分输入 |
| P4 | 能力分类 | 使用分类名称匹配 |

核对结果进入 `maturity_mainline_match_result`。不一致项只输出待确认清单，不自动修改主工程核心 schema，不自动改写 `knowledge_items`。
