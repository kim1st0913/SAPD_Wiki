# SAPD Wiki Application Shell Implementation Spec V1

版本：V1
日期：2026-05-16
适用范围：全局导航 / 应用壳前端实现准备

本文档基于 Stitch 输出 `application-shell-v1.png`、`application-shell-v1-notes.md`、全局导航 Prompt、`nav-manifest.v1.json`、前端菜单与页面类型定义、Stitch 设计交接文档和当前 `frontend/capability-browser/` 代码结构整理。

本文件只定义后续实现规格，不代表本轮已经修改运行中的前端代码。

## 1. Stitch 输出概述

### 1.1 顶部栏

Stitch 输出采用固定顶部栏，用于承载：

- 左侧品牌标识：`SAPD Wiki`。
- 中间全局搜索：占位文案为搜索知识、能力、标准、指南等全站对象，并展示快捷键提示。
- 右侧工具入口：通知、设置、数据 / 工作区入口、用户身份。

实现规格：

- 顶部栏应作为 `TopBar` 组件独立存在。
- 顶部栏高度建议保持紧凑，参考 Stitch notes 中的 `topbar-height: 56px`。
- 搜索是入口，不在 Application Shell 阶段实现完整全文检索逻辑。
- 工具图标应使用一致的按钮尺寸和 focus 状态，不做装饰性动效。

### 1.2 左侧导航

Stitch 输出采用固定左侧导航，一级菜单完整展示，并支持部分二级菜单展开。

图中可见一级入口包括：

- 首页
- 安全指南
- 安全能力映射
- 信息化环境安全能力映射
- 开发安全
- 数据安全
- 安全知识
- 安全标准 / 框架

实现规格：

- 左侧导航应作为 `SideNavigation` 组件独立存在。
- 一级菜单来源于 `nav-manifest.v1.json` 的 `navigation` 顶层数组。
- 菜单宽度不应过度占用横向空间，建议以 240px 为初始参考。
- 当前选中一级菜单应有清晰背景、文字和图标状态。
- 不建议使用 Stitch 图里的粗重彩色侧边条作为唯一选中状态，避免与项目设计规则中的侧边强调风险冲突；可用轻背景、字重、图标色和 1px 边界组合表达。

### 1.3 二级菜单

Stitch 输出展示了 `安全知识` 展开后的二级菜单，包括安全能力作用域目录、安全技术模块目录、安全工作清单目录、安全职能流程目录、安全工作职能目录、岗位 / 职能参考目录、Hype Cycle 等。

实现规格：

- 二级菜单应由 `NavigationGroup` 组件负责渲染。
- 二级菜单来源于对应一级菜单的 `children`。
- 展开 / 收起状态由前端 UI 状态维护，不改变 Manifest 数据。
- 有二级菜单的一级项应展示展开指示。
- 无二级菜单的一级项点击后直接切换页面。
- 二级菜单不应挤压主内容区，不应生成独立第二侧栏，除非后续页面需要更复杂的信息架构。

### 1.4 全局搜索

Stitch 输出中的全局搜索位于顶部栏中心区域，是跨知识、能力、标准、指南的全站入口。

实现规格：

- 组件名建议为 `GlobalSearch`。
- Application Shell 阶段只实现搜索入口、输入框、快捷键提示和基础交互状态。
- 不在本阶段实现跨数据包检索、命令面板、搜索结果面板或索引逻辑。
- 后续可通过 `dataClient` 或 `/api/v1/*` 接入搜索结果。

### 1.5 页面标题区

Stitch 输出在主内容顶部提供页面标题区，包含：

- 面包屑：例如 `首页 > 安全能力映射`。
- 页面标题：例如 `安全能力映射`。
- 页面类型或优先级标签：例如 `P1 工作台`。
- 页面说明文案。
- 右侧页面操作：例如导出数据、编辑映射。

实现规格：

- 面包屑由 `Breadcrumb` 组件渲染。
- 标题区由 `PageHeader` 组件渲染。
- `priority` 可以作为规划标签显示，但不应强行决定 UI 排序。
- 操作按钮应由具体页面声明，Application Shell 只提供插槽或容器。
- 页面说明应来自页面配置或 ViewModel，不在壳组件中硬编码业务解释。

### 1.6 主内容区

Stitch 输出为数据密集型工作台预留大面积主内容区，背景为浅色工作区，内容以分栏、表格、树和局部关系摘要承载。

实现规格：

- 主内容区建议由 `MainContentLayout` 组件承载。
- 主内容区应填满顶部栏和左侧导航之外的剩余空间。
- 页面内容应保持独立，避免 Application Shell 与业务组件互相耦合。
- 主内容区需支持普通目录页、文档页、标准页、工作台页和预留页多种页面类型。

### 1.7 三栏工作台承载结构

Stitch 输出中的工作台示例为三栏结构：

- 左栏：能力目录 / 对象目录 / 页面内导航。
- 中栏：当前能力或对象的主工作区，承载对象头、标签、表格、矩阵和局部关系摘要。
- 右栏：关联模块、来源证据、统计摘要等右侧洞察区。

实现规格：

- 通用三栏结构建议抽象为 `WorkbenchLayout`。
- 左栏宽度建议可配置，初始约 280px 至 360px。
- 中栏应优先获得剩余空间。
- 右栏建议可折叠，初始约 300px 至 360px。
- 1440px 下应确保中栏不被挤压；必要时右栏可收起为按钮或底部折叠区。
- 1920px 下可完整展示左中右三栏。

### 1.8 右侧详情 / 证据 / 摘要区域

Stitch 输出右侧包含 `关联模块清单`、`来源证据`、`统计摘要` 等区域。

实现规格：

- 右侧区域建议抽象为 `RightInsightPanel`。
- 该区域只承载页面级摘要、详情、证据和辅助洞察，不承担业务关系生成。
- 来源证据默认折叠，避免压缩主工作区。
- 非业务字段只能出现在折叠后的来源证据细节中，不进入主展示区。

## 2. 与当前工程前端结构的差异

### 2.1 导航结构差异

当前 `frontend/capability-browser/index.html` 中左侧导航仍是静态按钮组，主要围绕现有关系视图和知识维护入口：

- `关系总览`
- `安全能力映射`
- `信息化环境维度`
- `LC-AP开发安全生命周期`
- `数据生命周期维度`
- `专项知识维护`
- `说明与视图`

Stitch 输出与 `nav-manifest.v1.json` 要求的目标导航是全站信息架构，不再只是当前 MVP 页面切换。

差异处理：

- 后续实现应把静态 HTML 导航迁移为 Manifest 驱动的导航渲染。
- 当前已有页面入口需要映射到新的一级菜单或二级菜单，不应简单删除。
- `LC-AP开发安全生命周期` 后续应作为受控专项投影处理，不应在 Application Shell 中被误提升为 P1 核心工作台。

### 2.2 布局差异

当前前端已有 `app-shell`、`app-sidebar`、`topbar`、`workspace-stage` 等结构，但主要围绕单页静态 MVP 页面切换。

Stitch 输出要求更明确的全局应用壳：

- 顶部栏更偏全站工具区。
- 左侧导航是全站一级 / 二级菜单。
- 页面标题区独立于业务工作台。
- 工作台布局由页面内容区承载，而不是写死在 `index.html` 的多个 `main` 中。

差异处理：

- 先保留现有页面可用性。
- 后续新增壳组件时应逐步接管导航和标题区，不一次性重写所有业务页面。
- 业务页面内部的树、表格、关系区保持由现有组件和 ViewModel 驱动。

### 2.3 页面容器差异

当前页面容器以多个 `main` 节点切换显示为主，例如 `overviewWorkspace`、`capabilityWorkspace`、`environmentWorkspace`、`devLifecycleWorkspace`。

目标实现应转为：

- `AppShell` 负责全局框架。
- `MainContentLayout` 负责页面标题区和内容容器。
- 页面模板根据 `type` 识别，选择 workbench、directory、document、standard 或 placeholder 等承载方式。

### 2.4 菜单层级差异

当前 MVP 导航只有分组标签和一级按钮，没有完整的 Manifest 二级层级。

目标菜单层级：

- 顶层 `navigation` 作为一级菜单。
- `children` 作为二级菜单。
- 子项仍保留 `type`、`route`、`priority`，供页面模板和规划使用。

实现注意：

- `priority` 不应强行决定 UI 排序，排序以 Manifest 数组顺序为准。
- `type` 不应变成业务逻辑开关，只用于选择页面模板和空状态策略。

### 2.5 样式差异

当前 `styles.css` 已有较多历史样式，包含多种面板、表格、关系组件和后续追加的布局规则。

Stitch 输出更偏统一设计系统：

- 轻背景工作区。
- 固定导航与顶部栏。
- 1px 边界和层级灰度。
- 系统化按钮、搜索框、标签和面板样式。
- 数据密集表格，少用装饰卡片。

实现注意：

- 后续实现应先补应用壳相关 token 和布局类，不应为了套图大面积覆盖业务组件样式。
- 避免把 Stitch HTML 原样接入，尤其是内联样式、临时图标和不可维护的类名。
- 设计中出现的大按钮或图标应转译为当前项目一致的按钮和图标策略。

### 2.6 组件拆分差异

当前已有 `components/AppShell.js`，但它主要提供能力页工作区挂载和摘要渲染，并不是真正的全局 Application Shell。

目标组件拆分应把全局壳与业务页面拆开：

- 全局壳：导航、顶部栏、搜索、标题区、页面容器。
- 工作台布局：三栏承载结构。
- 业务组件：能力树、环境树、关系矩阵、来源证据、维护表格等。

后续实现时可选择重命名现有 `AppShell.js` 的内部职责，或新增更明确的壳组件文件，但必须避免同时存在两个语义冲突的 `AppShell`。

## 3. 推荐组件拆分

| 组件 | 建议职责 | 不应承担 |
|---|---|---|
| `AppShell` | 组合顶部栏、侧边导航、主内容区，管理当前页面容器和整体布局 | 不生成业务关系，不读取原始 JSON，不直接实现具体页面内容 |
| `TopBar` | 品牌、全局搜索入口、全局工具按钮、用户区域 | 不实现业务搜索结果，不处理页面内筛选 |
| `SideNavigation` | 渲染一级导航、当前选中状态、底部本地状态或快捷入口 | 不写死业务页面列表，不承担页面数据加载 |
| `NavigationGroup` | 渲染可展开 / 收起的二级菜单和子项选中态 | 不改变 Manifest 数据，不做权限或数据推断 |
| `GlobalSearch` | 搜索输入框、快捷键提示、打开搜索面板的入口状态 | 不在本阶段实现全文检索和跨包排名 |
| `Breadcrumb` | 根据当前 route 或页面配置展示位置路径 | 不把业务对象路径与全站导航路径混在一起 |
| `PageHeader` | 页面标题、说明、标签、状态、页面操作插槽 | 不硬编码某个页面的业务说明和按钮逻辑 |
| `MainContentLayout` | 提供通用页面内容容器，承载不同页面模板 | 不直接渲染能力、环境、标准等业务数据 |
| `WorkbenchLayout` | 提供左中右三栏工作台结构和响应式折叠策略 | 不实现 LocalRelationMap 业务逻辑 |
| `RightInsightPanel` | 承载详情、来源证据、摘要、辅助信息，支持折叠 | 不在主展示区暴露来源原始字段 |

## 4. 导航 Manifest 映射方式

Manifest 文件：`frontend/design-handoff/navigation/nav-manifest.v1.json`

### 4.1 一级菜单

- 来源：`navigation` 顶层数组。
- 字段使用：
  - `id`：稳定菜单键。
  - `label`：显示名称。
  - `route`：目标路由或视图标识。
  - `type`：页面模板识别。
  - `children`：二级菜单。

### 4.2 二级菜单

- 来源：一级菜单的 `children`。
- 有 `children.length > 0` 的一级菜单支持展开 / 收起。
- 二级菜单点击后进入对应 route 或静态视图映射。
- 子级仍可携带 `type`，用于后续页面模板识别。

### 4.3 `type` 的使用方式

`type` 用于页面模板识别，例如：

- `application-shell`：全局导航 / 应用壳。
- `document-hub`：指南集合页。
- `document-page`：单篇文档页。
- `capability-mapping-workbench`：安全能力映射工作台。
- `environment-mapping-workbench`：信息化环境映射工作台。
- `domain-module`：专题模块或独立业务模块。
- `knowledge-directory`：知识目录页。
- `standard-framework-directory`：标准 / 框架目录。
- `standard-framework-page`：单个标准 / 框架页。
- `placeholder-page`：预留页。

实现时不得让 `type` 绕过 `dataClient` 或 `/api/v1/*` 直接读取原始数据。

### 4.4 `priority` 的使用方式

- `priority` 仅用于规划、设计交接和页面建设阶段识别。
- UI 排序不应由 `priority` 自动重排，默认以 Manifest 数组顺序为准。
- 可在页面标题区或设计文档中显示 `P0`、`P1`、`P2`、`P3`，但不应让用户误以为这是业务状态。

## 5. 关于本地关联摘要的处理说明

Stitch 图中主工作区下方出现的“本地关联摘要”只作为主内容区承载示例。

后续实现必须遵守：

- Application Shell 实现阶段不要求完整实现 `LocalRelationMap` 业务逻辑。
- `LocalRelationSummary` / `LocalRelationMap` 应在后续“安全能力映射工作台”专项设计中进一步细化。
- Codex 不得把 Stitch 图中的关系区直接固化为最终业务组件。
- 关系摘要的业务输入必须来自 `capability-workbench.json`、后端投影或 ViewModel 安全字段。
- 该区域不能临时从原始 JSON、Sheet 字段或调试字段中推断关系。
- 如果 Application Shell 阶段需要占位，只能使用页面插槽或空容器，文案应说明“由具体工作台提供”。

## 6. 不允许修改的内容

Application Shell 实现阶段不得修改：

- ETL。
- 数据库。
- 数据模型。
- 导出 JSON 结构。
- 业务字段含义。
- 已有数据契约含义。
- 三份 workbench JSON 的结构。
- `dataClient` 的数据来源边界，除非另有数据契约任务明确要求。

前端实现阶段也不得：

- 直接把 Stitch HTML 原样接入运行代码。
- 引入大型 UI 框架。
- 引入新依赖，除非另有批准。
- 破坏现有页面可用性。
- 为套图而重写业务 ViewModel。
- 在组件中实现 ETL、主数据归一、跨表匹配、成熟度评分或业务关系推断。
- 在主展示区显示 `sheet`、`row`、`column`、`raw_value`、`source_file`、`import_id`、`source_id`、`source_ref`、`source_label`、`debug`、`raw`、`metadata`、`intermediate`、`generated_at`。

## 7. 后续实现阶段建议

建议按以下顺序推进，避免一次性重构全站：

1. 先实现应用壳组件：建立 `AppShell` 的全局布局边界，保留现有页面切换能力。
2. 再接入导航配置：读取或内置转换 `nav-manifest.v1.json`，完成 Manifest 到现有视图的映射表。
3. 再实现顶部栏：落地 `TopBar` 和 `GlobalSearch` 的入口形态，不实现复杂搜索结果。
4. 再实现左侧导航和二级菜单：落地 `SideNavigation` 与 `NavigationGroup`，支持展开 / 收起。
5. 再实现页面标题区和面包屑：落地 `Breadcrumb` 与 `PageHeader`，页面操作以插槽方式接入。
6. 再实现通用三栏 `WorkbenchLayout`：先支持能力页和环境页承载，不迁移业务逻辑。
7. 最后逐页迁移业务页面：安全能力映射页、信息化环境映射页、知识目录、标准 / 框架、指南文档和 LC-AP 受控专项页分别收口。

每一步都应保持现有页面可打开、可切换、可读取数据。

## 8. 验收标准

Application Shell 前端实现完成后，应至少满足以下标准：

- 1440px 下主内容区不被左侧导航和右侧面板挤压，数据密集型表格仍可阅读。
- 1920px 下主内容区能完整承载左中右三栏工作台。
- 一级菜单完整可见，或在高度不足时可滚动且不遮挡底部状态。
- 二级菜单可展开 / 收起。
- 全局搜索入口清晰，focus 状态可见。
- 页面标题区清晰，包含面包屑、标题、说明、标签和页面操作容器。
- 主内容区能够承载数据密集型工作台，不变成营销首页。
- 不出现大面积 Hero 区。
- 不出现复杂网络图作为首页或 Application Shell 默认内容。
- 不出现卡片墙作为关系工作台主表达。
- 来源证据默认折叠，不挤压主工作区。
- 当前安全能力映射、信息化环境、LC-AP、专项知识维护等现有前端页面不因应用壳整理而失效。
- 页面数据仍通过 `dataClient`、`/api/v1/*` 或后端生成的离线兼容包进入前端。
- 主展示区不暴露非业务字段。

## 9. 当前风险与实现提醒

| 风险 | 说明 | 建议处理 |
|---|---|---|
| Stitch 示例被误当成最终业务页面 | 图中的关系摘要和模块清单是承载示例 | Application Shell 只实现容器，能力页专项再设计业务组件 |
| 当前 `AppShell.js` 语义已被局部使用 | 现有文件主要服务能力页挂载和摘要渲染 | 后续实现前先确定是重命名旧职责还是扩展为真正全局壳 |
| 导航口径迁移过快 | 当前 MVP 入口与 Manifest 全站菜单不一一对应 | 建立 route 到现有 view 的映射表，逐页迁移 |
| 样式文件历史规则较多 | `styles.css` 已承载大量页面样式 | 先追加壳层样式 token 和布局类，避免大面积覆盖 |
