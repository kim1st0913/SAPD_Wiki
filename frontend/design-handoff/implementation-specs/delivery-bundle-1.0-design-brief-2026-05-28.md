# Delivery Bundle 1.0 设计团队沟通简报

本文档用于设计团队内部沟通 SAPD Wiki 打包交付方案。它不是开发实现说明，也不是安装器技术文档，而是把“预构建数据库交付版”的用户体验、页面状态、信息层级和设计产出说清楚。

架构评估入口见 `docs/01-architecture/delivery-bundle-1.0-prebuilt-database.md`；正式工程设计见 `docs/09-delivery/delivery-bundle-1.0-prebuilt-database.md`。

## 1. 一句话定义

SAPD Wiki Delivery Bundle 1.0-alpha 是一个面向内部团队快速分发的 ZIP 解压即用知识库运行包：制作者提前完成原始资料导入、清洗、审查、审批并构建只读基础库；用户解压后双击启动脚本或后端可执行文件，系统读取 `sapd_wiki_base.sqlite3` 并把用户自己的备注、收藏、个人标签和新增内容写入 `sapd_wiki_user.sqlite3`。用户无需 Python、Node、Docker、ETL 或初始化命令，即可在浏览器中打开本地工作台。

## 2. 设计目标

设计要解决的不是“怎么导入数据”，而是“让用户相信这个本地知识库已经准备好了，可以直接用”。

核心体验目标：

| 目标 | 设计含义 |
|---|---|
| 零开发感 | 不出现 Python、Node、Docker、ETL、SQLite CLI、端口号、数据库路径等开发概念 |
| 快速进入工作台 | 首次启动完成检查后直接进入工作台，不做营销式首页 |
| 本地可信 | 明确告诉用户数据在本机、可离线、不会上传 |
| 数据可升级 | 基础库更新不能覆盖用户自己的备注、收藏、标签和新增内容 |
| 可恢复 | 数据损坏、升级失败或资源缺失时，用户能看到清楚的修复入口 |
| 低打扰 | 初始化、校验、修复尽量后台完成，只在需要用户判断时打断 |

## 3. 用户角色

| 用户 | 需求 | 不需要 |
|---|---|---|
| 普通业务用户 | 打开应用、搜索、浏览、查看关系、导出资料 | 选择数据库、运行命令、理解 ETL |
| 咨询顾问 | 解压或安装后快速演示、离线使用、把包交给客户 | 维护原始资料、修改 parser、调试后端 |
| 内部维护者 | 构建发布包、验证数据版本、回滚异常版本 | 让最终用户接触维护流程 |

## 4. 推荐交付形态

设计沟通时统一按“ZIP 优先，安装包后置”表达：

| 形态 | 面向对象 | 设计关注 |
|---|---|---|
| zip 解压即用包 | P0，内部团队快速传递 | 解压后的 `README-FIRST.md`、启动脚本、浏览器打开后的首屏状态、不要让用户误以为要安装依赖 |
| macOS / Windows 安装包 | P1，正式交付用户 | 安装完成后桌面应用体验、首次启动状态、升级提示 |

当前先围绕 ZIP 形态做设计；安装包进入应用后的体验后续应尽量复用 ZIP alpha 的启动状态、数据状态和故障处理语言。

## 4.1 必须锁定的工程边界

设计稿和说明文案必须默认以下边界成立：

```text
sapd_wiki_base.sqlite3
只读基础知识库，由制作者 / 管理员提前构建、验证、冻结和发布

sapd_wiki_user.sqlite3
用户自己的备注、收藏、个人标签、覆盖视图、修正建议、用户新增知识和用户导入审查数据
```

用户所谓“修改基础知识”，在界面上应表达为：

- 添加个人备注；
- 收藏；
- 添加个人标签；
- 隐藏或调整个人视图；
- 提交修正建议；
- 新增本地知识对象或本地关系。

不要设计“直接编辑官方基础库”的体验。基础知识库升级时，用户内容必须保留。

## 5. 首次启动用户旅程

```text
获得 zip
→ 解压到本机目录
→ 双击 `start-windows.bat`、`start-macos.command` 或后端可执行文件
→ 应用检查本地数据状态
→ 启动本地后端和静态前端服务
→ 自动打开浏览器
→ 校验完成
→ 进入知识库工作台
```

设计原则：

- 默认不出现“欢迎页”或“产品介绍页”；
- 如果初始化少于 2 秒，可只显示轻量启动状态；
- 如果初始化较久，显示进度状态和当前动作；
- 成功后进入当前主工作台，而不是停留在完成页；
- 失败时进入可修复状态，而不是显示技术错误堆栈。

## 6. 必要界面状态

设计团队需要覆盖以下状态。它们可以是启动页、轻量模态、应用壳顶部状态或系统级设置页的一部分。

| 状态 | 触发条件 | 用户看到什么 | 主操作 |
|---|---|---|---|
| 正在准备本地知识库 | 首次启动，未发现运行库 | 一句话状态 + 轻量进度 | 无需操作 |
| 准备完成 | 数据部署和校验成功 | 短暂成功反馈 | 自动进入工作台 |
| 已就绪 | 非首次启动，运行库和资源正常 | 直接进入工作台，可在关于页看到数据版本 | 无需操作 |
| 数据需要修复 | 运行库缺失、资源 hash 不一致 | “本地数据可能损坏，可从随包数据修复” | 修复 |
| 版本需要升级 | 应用版本和数据版本不兼容 | “当前数据包需要升级后使用” | 查看升级说明 |
| 后端不可用，离线只读 | 内置本地后端启动失败但 JSON fallback 可用 | “部分功能暂不可用，当前以只读模式浏览” | 重试 / 查看详情 |
| 用户库需要备份或迁移 | App 升级后用户库 schema 需要升级 | “将先备份你的个人数据，再完成升级” | 继续 / 稍后 |

## 7. 信息架构建议

应用内部建议增加一个轻量入口：

```text
关于 / 数据状态
├─ 应用版本
├─ 数据版本
├─ 用户数据状态
├─ 数据更新时间
├─ 本地数据状态
├─ 离线可用状态
├─ 修复本地数据
├─ 备份个人数据
├─ 导出诊断包
└─ 打开导出目录
```

注意：

- 不要把它设计成开发者控制台；
- 不展示数据库绝对路径作为主信息；
- 不展示端口号、进程名、SQLite 文件名作为普通用户信息；
- “查看技术详情”可以折叠在维护者区域，但默认不展开。

## 8. 推荐文案

可用文案方向：

| 场景 | 推荐文案 |
|---|---|
| 初始化中 | 正在准备本地知识库 |
| 校验中 | 正在校验随包数据 |
| 成功 | 本地知识库已就绪 |
| 修复入口 | 修复本地数据 |
| 用户库升级 | 正在备份并升级你的个人数据 |
| 用户数据说明 | 你的备注、收藏和个人标签会保存在本机，不会被基础库更新覆盖 |
| 离线说明 | 所有知识库数据均在本机使用，可离线浏览 |
| 失败说明 | 本地数据未能正常加载，可以尝试从随包数据修复 |

避免文案：

- “正在运行 ETL”
- “请选择 SQLite 数据库”
- “请启动 Python 后端”
- “请执行初始化脚本”
- “端口被占用”
- “JSON fallback 模式”
- “正在修改基础库”

## 9. 视觉语气

打包交付相关界面应保持“工具型、可信、低打扰”：

- 不做大幅营销 hero；
- 不用夸张插画或庆祝动效；
- 状态反馈要清楚，但不要抢过主工作台；
- 错误提示要可恢复，不要让用户感觉系统坏掉；
- 颜色应延续当前 SAPD Wiki 工作台的蓝灰、白底、低阴影风格。

## 10. 设计交付物

建议设计团队输出：

1. 首次启动准备态界面；
2. 初始化失败 / 修复本地数据界面；
3. 关于 / 数据状态面板；
4. 升级提示状态；
5. 个人数据备份 / 用户库升级提示；
6. 诊断包导出入口；
7. zip 包内 `README-FIRST.md` 的一页式阅读版视觉稿；
8. macOS / Windows 包交付说明中的截图占位。

## 11. 不在本轮设计范围

本轮不要设计：

- 用户登录、注册、账号体系；
- 在线更新中心；
- 用户自行导入 Excel / PDF / PPT / DOCX；
- ETL 配置器；
- 数据库选择器；
- 直接编辑官方基础库；
- 开发者调试控制台；
- 多租户、权限和组织管理。

这些会把普通用户交付版带回开发工具方向，和 Delivery Bundle 1.0 的目标冲突。

## 12. 与当前项目进度的关系

当前项目主线仍是 Frontend Baseline 1.0 的关系工作台校正。Delivery Bundle 1.0 的设计沟通优先级提高，但工程实现不应立即打断当前页面和数据闭环。

对当前设计工作的明确影响：

- 后续页面设计必须保留 `dataClient` / `/api/v1/*` / JSON fallback 的边界，不新增直接读原始数据的页面；
- 后续数据和交互设计必须默认 `base/user` 双库分离，用户动作写入用户库或 overlay，不改写基础库；
- 进入正式交付前，基础对象需要稳定业务键 `stable_key` 或 deterministic public id，否则用户备注、收藏和关系在基础库升级后会断裂；
- 页面主展示区继续禁止非业务字段泄露；
- 设计稿要预留“本地数据状态 / 修复 / 版本信息”入口；
- 工作台首页仍应是可用知识库，不改成营销式欢迎页。

## 13. 设计评审问题

内部评审时建议直接讨论以下问题：

1. 首次启动自动初始化时，是否需要可见进度，还是只展示短暂启动状态？
2. “关于 / 数据状态”放在顶部栏、设置入口，还是帮助菜单？
3. 当本地后端不可用但 JSON 可用时，是否允许用户进入只读工作台？
4. zip 解压即用版本的 `README-FIRST.md` 是否需要更强的双击启动引导？
5. 修复本地数据是否需要二次确认和备份提示？
6. 用户“修改基础知识”的入口，应统一叫“修正建议”还是“个人覆盖”？
7. 个人数据备份和诊断包导出应该放在同一个数据状态面板，还是分成两个入口？

## 14. 当前推荐决策

建议本轮设计先按以下决策推进：

- 首次启动默认自动准备数据；
- 成功后直接进入工作台；
- 设置或关于区域提供数据状态；
- 异常时只暴露“修复 / 重试 / 查看简要说明”；
- 用户个人内容写入用户库，基础库只读；
- 需要显式设计个人数据备份和诊断包导出入口；
- ZIP alpha 先服务内部团队快速分发；安装包体验后置并尽量复用同一套界面状态；
- 不引入登录、导入、数据库选择和开发者设置。
