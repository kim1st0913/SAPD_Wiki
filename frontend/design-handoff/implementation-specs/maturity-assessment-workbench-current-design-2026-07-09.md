# 工作台成熟度评估模块当前设计与业务逻辑说明

本文档用于把当前 SAPD Wiki 中 `工作台 > 成熟度评估` 已有的一般前端设计、信息架构和成熟度业务逻辑整理成可交接说明。它不是新的视觉方案，也不是后端实现规格的最终版；后续进入正式实现前，还需要补齐 maturity 专用 API / ViewModel 契约。

## 1. 当前结论

`工作台 > 成熟度评估` 当前已经有静态前端 mock 和产品入口设计，主要表达评估项目管理、项目详情、评分填报和报告导出入口。它还没有接入真实 maturity 数据、没有实现评分算法、没有实现模板导入、没有实现图表计算。

当前定位：

| 项目 | 当前口径 |
|---|---|
| 页面归属 | `工作台 > 成熟度评估` |
| 路由 | `/workbench/maturity`、`/workbench/maturity/project-001` |
| 旧规划路由兼容 | `/sapd-maturity-assessment` 归一到 `/workbench/maturity` |
| 页面类型 | `workbench-page` / `domain-module` |
| 当前实现性质 | 静态 mock 页面，使用演示项目数据 |
| 正式数据来源 | 后续 maturity 专用数据契约 |
| 能力权威源 | `知识库字典 > 安全能力清单` |
| 说明类内容归属 | `安全指南 > 成熟度模型使用指南` |

设计边界：

- 不把成熟度模型说明、等级解释和模板填写说明塞进评估工作台主流程；
- 不在 maturity 模块内维护独立安全能力主数据；
- 不把客户评估数据、评分结果、证据、报告快照写入 `knowledge_items`；
- 不在前端组件内实现 ETL、主数据归一、跨表匹配、评分和客户评估结论生成；
- 不把当前 mock 中的项目、分数、图形当作真实评估结果。

## 4. 当前视觉与交互风格

当前成熟度页面沿用工作台原型样式：

- 整体是浅色、低噪声、本地工作台风格；
- 使用 `workbench-route-page` 作为页面容器；
- 使用紧凑标题区 `workbench-section-title`；
- 使用项目卡片、状态 pill、筛选 chip、项目表格和右侧摘要面板；
- 详情页使用三栏布局：左侧维度导航、中间表单、右侧结果摘要；
- 选中态使用浅蓝背景和蓝色边框；
- 状态使用低饱和颜色区分：
  - `is-good`：完成 / 正向状态；
  - `is-warn`：暂存 / 待处理状态；
  - `is-muted`：占位 / 次要操作。

当前视觉只是一般前端设计。正式成熟度评估页面不应继续扩大卡片数量，应优先形成更像顾问工作台的结构：

- 项目列表用表格；
- 匹配审查用队列 + inspector；
- 评分填报用能力树 / 关注点矩阵 + 右侧证据；
- 结果总览用分层表格和可解释摘要；
- 图表只展示后端生成的结果，不在前端即时推断。

## 5. 成熟度业务逻辑

### 5.1 模块定位

maturity 模块是 SAPD Wiki 主工程下的独立业务模块。它读取主工程安全能力知识库，生成客户成熟度评估输入、匹配、评分、差距和报告，但不污染知识主数据。

业务边界：

```text
SAPD Wiki 主知识库：维护安全能力、关注点、服务、模块、流程、职能、标准和来源追踪
maturity 模块：执行客户评估项目、输入解析、匹配审查、评分、差距分析和报告快照
```

### 5.2 模型来源

成熟度模型设计严格参考样本文档中的固定业务逻辑：

- `sample文档介绍.docx` 第 3.1 章：网络安全能力成熟度模型；
- `sample文档介绍.docx` 第 4 章：网络安全能力成熟度评估。

后续代码只能结构化实现这两部分逻辑，不能重新发明另一套成熟度模型。

### 5.3 评分对象

正式评分对象收敛为两类：

| 评分对象 | 对应主工程对象 | 说明 |
|---|---|---|
| 安全能力 | `capability` | L2 安全能力，可直接评分，也可由关注点聚合 |
| 安全关注点 | `capability_focus` | 关注点评估，是连接能力树和成熟度基准的核心对象 |

安全技术服务不是独立成熟度评分对象。它作为技术输入，用于支撑 `platform_tool_score` 的证据、匹配线索和技术覆盖说明。

### 5.4 三维评分模型

V1 采用：

```text
安全能力维 × 落地要素维 × 成熟度等级维
```

| 维度 | 说明 |
|---|---|
| 安全能力维 | 读取主工程权威能力树，评分对象为 `capability` 和 `capability_focus` |
| 落地要素维 | 评估组织、流程、平台工具、数据支撑是否具备 |
| 成熟度等级维 | 使用 L0-L5 表示成熟度 |

固定四个评分要素：

| 要素 | 字段 | 默认权重 |
|---|---|---:|
| 组织与角色 | `organization_role_score` | 0.25 |
| 制度与流程 | `process_system_score` | 0.25 |
| 平台与工具 | `platform_tool_score` | 0.25 |
| 数据与信息 | `data_information_score` | 0.25 |

### 5.5 成熟度等级

| 等级 | 名称 | 默认分 | 判断含义 |
|---|---|---:|---|
| L0 | 未覆盖 / 无有效证据 | 0 | 没有有效输入、证据或匹配 |
| L1 | 临时执行 | 20 | 有零散实践，依赖个人经验 |
| L2 | 计划跟踪 | 40 | 有职责、计划、局部流程或局部工具，能重复执行但覆盖有限 |
| L3 | 充分定义 | 60 | 组织、流程、技术和运营较完整，能在主要范围稳定落地 |
| L4 | 量化控制 | 80 | 有指标、审计、监控、报表或效果度量 |
| L5 | 持续优化 | 95 | 能基于度量、事件、审计或风险变化持续改进 |

### 5.6 评估流程

正式评估流程建议为：

```text
创建评估项目
→ 选择模型版本、模板版本和知识库快照
→ 生成或导入评估模板
→ 解析客户输入与证据
→ 标准化输入项
→ 匹配安全能力 / 关注点
→ 低置信度匹配进入人工审查
→ 四要素评分
→ 聚合到关注点 / 能力 / 能力域 / 总体
→ 生成差距项与改进建议
→ 生成报告快照和导出文件
```

### 5.7 匹配与审查逻辑

自动匹配优先级：

| 优先级 | 方法 | 分数建议 | 处理 |
|---|---|---:|---|
| P0 | 能力编码精确匹配 | 100 | 自动接受 |
| P1 | 标题 / 别名精确匹配 | 90 | 自动接受 |
| P2 | 关系扩展匹配 | 70-85 | 高分可接受，低分需审查 |
| P3 | 关键词规则匹配 | 50-75 | 多数需要审查 |
| P4 | 本地模糊文本匹配 | 40-70 | 只作候选 |

候选状态：

| 分数 | 状态 | 说明 |
|---:|---|---|
| 85-100 | `auto_accepted` | 可自动进入评分，但保留审查记录 |
| 60-84 | `needs_review` | 进入人工审查 |
| 40-59 | `weak_candidate` | 仅参考，不直接评分 |
| 0-39 | `unmatched` | 未匹配 |

### 5.8 与主工程权威数据的关系

能力数据只读引用 `知识库字典 > 安全能力清单`。maturity 模型基准中的能力分类、L1 能力域、L2 安全能力、能力关注点和安全技术服务输入必须先与主工程治理数据做一致性核对。

核对对象：

| maturity 基准对象 | 主工程权威对象 | 核对目的 |
|---|---|---|
| 能力分类 | `capability_category` | 分类名称和层级是否一致 |
| L1 高阶战略能力 | `capability_domain` | L1 能力域是否存在、命名是否一致 |
| L2 安全能力 | `capability` | L2 能力是否存在、归属是否一致 |
| 能力关注点 | `capability_focus` | 编码、标题、描述和父级能力是否一致 |
| 作用域安全技术服务 | 主工程安全技术服务对象 | 作用域、服务名称、服务归属和能力关系是否一致 |

不一致项进入人工确认，不自动修改主工程：

- `missing_in_mainline`
- `missing_in_maturity`
- `name_conflict`
- `parent_conflict`
- `scope_conflict`
- `service_conflict`
- `ambiguous_match`

## 6. 正式数据对象与页面映射

后续正式页面应消费后端或 maturity 服务层输出的 ViewModel，不直接读原始表、客户文件或运行表。

| 页面区域 | 后端对象 | 前端展示建议 |
|---|---|---|
| 项目列表 | `assessment_project` | 表格：客户、项目、模型版本、状态、等级、总分、最近更新、操作 |
| 来源文件 | `assessment_source_file` | 折叠来源面板：文件类型、hash、用途、敏感级别 |
| 原始输入 | `assessment_input_raw` | 默认不进主界面，只在证据 / 调试受控区查看 |
| 标准化输入 | `assessment_input_normalized` | 评分表和匹配审查的输入行 |
| 主线一致性核对 | `maturity_mainline_match_result` | 模型启用前的差异审查表 |
| 输入匹配结果 | `maturity_match_result` | 匹配审查队列和候选 inspector |
| 评分结果 | `maturity_score_result` | 项目详情、能力明细、维度分数、等级 |
| 差距项 | `maturity_gap_item` | 差距列表、优先级、目标等级 |
| 改进建议 | `maturity_recommendation` | 建议列表、责任方、阶段 |
| 报告快照 | `maturity_report_snapshot` | 报告预览、Markdown / HTML / JSON 导出 |

## 7. 正式前端页面建议

当前 mock 已经表达了两个页面，但正式实现建议拆成四个可渐进落地的视图：

| 视图 | 作用 | 首版是否需要 |
|---|---|---|
| 评估项目列表 | 管理项目、筛选状态、继续评估、导出报告 | 需要 |
| 评估项目详情 | 展示项目摘要、来源文件、当前状态、总分和等级 | 需要 |
| 匹配审查 | 审查低置信度能力 / 关注点匹配 | 建议 M2/M3 引入 |
| 评分填报 / 结果明细 | 以能力树或关注点矩阵查看四要素评分、证据、差距和建议 | 需要 |

页面结构建议：

```text
工作台 > 成熟度评估
  ├─ 项目列表
  ├─ 项目详情
  ├─ 匹配审查
  ├─ 评分明细
  └─ 报告快照
```

正式设计应优先使用：

- 左侧项目 / 能力树；
- 中间表格 / 矩阵；
- 右侧详情 inspector；
- 折叠证据面板；
- 稳定的状态标签；
- 后端生成的评分解释。

不建议使用：

- 大面积营销式卡片；
- 伪雷达图或前端即时推断图；
- 独立能力主数据维护；
- 把方法论长文塞进工作台页面；
- 展示 `sheet`、`row`、`raw_value`、`metadata` 等原始字段。

| 缺口 | 说明 |

## 9. 后续实现顺序建议

建议顺序：

1. 先定义 `maturity` 后端数据契约和 ViewModel；
2. 把当前 `/workbench/maturity` 静态项目列表替换为后端项目投影；
3. 把项目详情页改成真实 `assessment_project`、`maturity_score_result`、`maturity_gap_item` 展示；
4. 增加匹配审查队列，复用工作台三栏思路；
5. 增加报告快照预览和导出入口；
6. `安全指南 > 成熟度模型使用指南` 已作为独立文档页承载方法论说明。

不建议下一步直接做复杂图表、复杂评分算法或完整 UI 重构。当前最应该先收紧的是数据契约和四要素评分页面结构。
